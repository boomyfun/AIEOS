## 2. The zero-friction principle

- The risk the concept names first: a one-line README fix that must pass through every artifact makes people remove the tool [AIEOS-concept.md:787]. The principle: "user nói ý định, AIEOS tự sinh các artifact; user chỉ duyệt khi risk đòi hỏi" [AIEOS-concept.md:789].
- "Fast path không phải bypass path": a low-risk task still has V0 (scope) and V1 (deterministic), is still written to the event log and stays traceable; only the human procedure is cut, never the control [AIEOS-concept.md:804].
- **The core runs no model.** The AIEOS core decides, grants, checks and records; it writes no code and runs no model (constitution INV-001) [docs/pre-genesis/constitution.md:27-28], from the concept's "Nó không viết code, không chạy model" [AIEOS-concept.md:162]. This is a rule, not a choice of this text; it changes only through the constitution's own route.
- **Who makes the artifacts** (proposed; reading of the decision agent, D-2238): the artifacts an intent needs are drafted by an agent working under a pulled task, where the launcher fixes the task and the agent pulls its Work Order through MCP [docs/specs/spec-06-mcp-protocol-and-work-orders.md:13], or written by the user; AIEOS checks them, records them and routes them for approval by risk. This reading reconciles the concept's own lines: "AIEOS tự sinh các artifact" [AIEOS-concept.md:789] and "AIEOS đề xuất" [AIEOS-concept.md:796] with the core that runs no model [AIEOS-concept.md:162], and with the drafting the concept gives to an AI ("AI quét repo, đề xuất") [AIEOS-concept.md:928] (decision D-2243). The dispatch, the agent pulling its own work, is the owner's answer to DM A43 Q6, "6 b" [docs/pre-genesis/decision-matrix.md:104], kept by decision D-2050 [docs/specs/spec-06-mcp-protocol-and-work-orders.md:95]; the owner may change the dispatch in one sentence. Listed in section 10 point 1.
- **Its cost, stated:** under this reading a larger intent's proposal set is drafted in a launched agent session, and each session needs a launch (section 5), so `aieos run` for a larger intent does not finish in one step; the owner may raise this (section 9).

## 3. The commands

One entry point, the bootstrap's CLI (proposed: a module of the bootstrap package run as a command; its installed name and how the owner starts it on the machine are not fixed here). Every command writes, where it writes, through the core's one writer [docs/specs/spec-02-aieos-file-format.md:45]; agents act through the protocol or the CLI, never by writing the project-state directory [docs/specs/spec-01-state-and-event-model.md:51].

- **`aieos init`** [AIEOS-concept.md:939]: creates the project-state layout of specification 2 section 3 [docs/specs/spec-02-aieos-file-format.md:25], a layout settled as the owner's, with `changes/` and `local/` (DM B7 note; A59, A60, F16) [docs/pre-genesis/decision-matrix.md:158]; it writes no constitution proposal: specification 2 names no file for one (its section 4.3 form is a change request), and `aieos import` drafts the proposals (revision 3; TASK-095). Running it on the self-build raises where the interim documents under `docs/plan/` and `docs/specs/` move, which specification 2 leaves open [docs/specs/spec-02-aieos-file-format.md:275]; open in section 10.
- **`aieos import`** [AIEOS-concept.md:928], [AIEOS-concept.md:939]: makes a task whose Work Order asks an agent to read the repository and draft the architecture and constitution proposals (proposed; the reading of section 2). Approving a constitution follows the constitution's own rule: it changes only through an approved change request, and the agent only proposes; for gov-AIEOS, while the A41 delegation is in force, the decision agent approves it in the owner's place, within the limits of CR-002 parts 4 and 8 [docs/pre-genesis/constitution.md:144]; once bound, an article changes only by a genesis amendment [docs/pre-genesis/constitution.md:145]. For a product project, the user approves ("human duyệt" [AIEOS-concept.md:928]); for a user who has chosen option "b", the AI approving in their place does, with the acts the user keeps (CR-002 part 9 points 3, 4 and 8) [docs/pre-genesis/CR-002-concept-errata.md:113-114] [docs/pre-genesis/CR-002-concept-errata.md:117-118].
- **`aieos run "<intent>"`** [AIEOS-concept.md:940], [AIEOS-concept.md:792-798]: records the intent (proposed), as a `claim` record that changes no task state and approves nothing (specification 1 §12 and specification 2's revision 11, both revised with this one; section 10). An intent has no changed paths, so the risk rules cannot class it: they class a change by the highest class among the rules that match its changed paths, and a path no rule matches gets no class and is never low [docs/specs/risk-rules-gov-aieos.md:16-17]. The core alone cannot class a bare intent, and it cannot draft a write-set from one, since that would take a model (section 2). So (proposed) a task contract is made from a task-contract template (not yet written): its write-set is given by the user or drafted by an agent under a pulled task (section 2); the core only fills the template's fixed fields, classes the contract by its write-set and records it. It classes under the rules read at the base [docs/specs/risk-rules-gov-aieos.md:18] (for gov-AIEOS that file; for a product project the risk rules of its own `project.yaml` [docs/specs/spec-02-aieos-file-format.md:29]); a declared risk lower than the rules give is not used [docs/specs/risk-rules-gov-aieos.md:19]. A task classed low still needs its contract approved before a lease (section 4) [docs/specs/spec-01-state-and-event-model.md:65], and still goes through V0, V1 and the event log [AIEOS-concept.md:804]. Otherwise (a class other than low, or no class), or when the intent needs more than one task, it makes a drafting task whose output is the proposal set of [AIEOS-concept.md:796] (requirement, specifications, tasks, risk and verification plan), routed to the approval flow (section 4).
- **`aieos status`** [AIEOS-concept.md:800-801]: progress, drift, tasks waiting for approval, requirements lacking assurance; each read from an existing reader of specifications 1, 3 and 4, and shown as "not available" where no reader exists yet (proposed). The MCP tool `status` of specification 6 serves the agent in a session; the command serves the user, from the same core reads (proposed).
- **`aieos tasks`** (proposed; added, not named at concept :997): the core function `list_tasks` (decision D-2040 C1) [docs/specs/spec-06-mcp-protocol-and-work-orders.md:14]: the tasks that may be taken. Fixed by sources: a task is READY only once approved with every dependency DONE [docs/specs/spec-01-state-and-event-model.md:65], and a lease is granted only on a task in READY or REWORK, one per task [docs/specs/spec-01-state-and-event-model.md:78]. Proposed: no live lease on the task, and its output form.
- **`aieos end <session>`** (proposed; added, not named at concept :997): ends a crashed session from outside any runtime session and outside the runtime's tool calls, which releases its leases, as specification 5 leaves to "specification 7's CLI" [docs/specs/spec-05-adapter-contract.md:119].
- **Outside any runtime** (proposed): `aieos end` and `aieos launch` refuse when the environment holds a session id or a project root, so that they are not run from an agent's shell inside a launched session; the limit for a determined agent stays as specification 5 states it (a nested runtime with a session id and a root it chooses) [docs/specs/spec-05-adapter-contract.md:120].
- **`aieos launch <task>`** (proposed; added, not named at concept :997): the launcher (section 5). Running it starts a runtime session with the MCP server connected; connecting the MCP server to the runtime is a Claude Code setting. For a product project the user runs it, or the machine asks the user's permission (proposed; revision 10). Specifications 5 and 6 still name these acts the owner's [docs/specs/spec-05-adapter-contract.md:92] [docs/specs/spec-06-mcp-protocol-and-work-orders.md:88]; their wording follows in later revisions of those specifications, not made here. For the AIEOS self-build (revision 10, proposed), since DM A73 [docs/pre-genesis/decision-matrix.md:134], which amends DM A51 item (4) [docs/pre-genesis/decision-matrix.md:112] for the self-build and for the acts it names, the decision agent decides launching and connecting real tools, each as its own decision, the owner told afterwards; what stays with the owner is every act at a permission prompt and whatever Claude's safety rules or the owner's command guard require the owner to permit, accounts, passwords, keys and money, and the decision agent's own authority; whatever A73 does not name stays kept (changes to the measurement protocol, CR-002 and other concept errata). The act itself is decided by the decision agent under DM A73; a task that carries out or changes such an act (building a runtime starter among them) is accepted by the owner under CR-002 part 4 limit 5 [docs/pre-genesis/CR-002-concept-errata.md:61] [docs/plan/master-plan.md:70]; whether that limit, which names what A51 item (4) keeps, still covers these acts after A73 amended A51 item (4) for the self-build is a reading of a concept erratum, kept with the owner (A73), and is not settled by this text. As shipped (revision 3; TASK-094), `aieos launch` has no runtime starter: inside a runtime it refuses, and otherwise it refuses with no runtime starter and starts nothing; the composition a launch would run, launcher.launch_outside, is in the core and is tested with stand-ins only. For TASK-094 only, the owner answered "có" (decision D-3154), so the decision agent approved and accepted that task in the owner's place; a real starter is not built; for the self-build its build is a task, accepted as the clause above says, and its connection and any run of the command with it are decided as the clause above says (revision 10).

## 4. The approval flow

- The concept's form: "[Approve] [Edit] [Reject]", then "chạy tự động tới khi cần escalate" [AIEOS-concept.md:797-798]. An approval is an authority record, one per task, bound to the task contract's hash (A42) [docs/pre-genesis/decision-matrix.md:103] [docs/specs/spec-01-state-and-event-model.md:93]; each answer is recorded as specification 1 §12 sets it (revision 3): Reject as an `authority` record with the same binding and `outcome` `fail`, never counted as an approval, Edit as a `claim` record holding the note, neither adding a task state; Edit returns the item to its drafter with the user's note (proposed).
- Who may approve what is not changed here. For gov-AIEOS in v0.1, until the governor exists, each task is accepted by one approval of the decision agent, except where CR-002 part 4 limits 5 or 8 make the owner the approver [docs/plan/master-plan.md:93]. For a product project that has not chosen option "b", A35 holds: the project starts at L1 and a person approves every task [docs/pre-genesis/CR-002-concept-errata.md:111]; with option "b", the AI approving in the user's place does, as section 3 says. The approval record of a requirement or a specification in the proposal set has no rule yet (A42 covers tasks): open (section 10). "auto-accept" [AIEOS-concept.md:793] is the concept's goal; nothing here raises an autonomy level or changes who accepts; any later change is its own decision.
- DEF-0020's option-b documents wait for, among others, the approval flow of M7 [docs/plan/master-plan.md:139]; they are outside gov-AIEOS's scope and are named here, not placed.

## 5. The launcher

- **Requirements**, carried in full from specification 5 [docs/specs/spec-05-adapter-contract.md:112] (and as specification 6 relies on them [docs/specs/spec-06-mcp-protocol-and-work-orders.md:26-27]): the session's start, submission and end are made outside the runtime session they govern, never by the agent's tool calls; each run of the runtime has a session id of its own, made by the launcher; the core's expiry runs before a grant; the runtime is not started without a grant, and a start without a grant is ended at once; on a grant the session id, the project root and the base are passed in the runtime's environment (the base as `AIEOS_BASE`, the base branch's tip at the grant, `main` for the self-build, written as 40 lowercase hexadecimal characters; that part proposed in specification 5); the observed read-set record is written before the lease is released, except as specification 5's point 10 says; the session is ended in every case. (Specification 5's revision 5 note on `AIEOS_BASE`: [docs/specs/spec-05-adapter-contract.md:138].) With them, specification 5 revision 6's stated limit at the same line: the core's end can refuse before any release, and the launcher built with TASK-094 falls back to the outside end (`end_outside`, the end of `aieos end`) after "argument" or "record", or directly when the contract's write set cannot be read, or when the granted answer is out of form but its session id is a string; a granted answer that is out of form and whose session id is not a string ends nothing; such a session, and other refused or failed ends, are left to `aieos end` or the lease's expiry (revision 3; reworded in revision 8, with the same meaning).
- **The Resume Check** runs before every grant: only CONTINUE and CONTINUE_WITH let the lease be granted [docs/specs/spec-03-resume-check-and-decision-engine.md:13], and the Work Order is issued only after them [docs/specs/spec-06-mcp-protocol-and-work-orders.md:51] [docs/plan/master-plan.md:79]; at a new session's start on a task still IN_PROGRESS under a lease it holds, the check is the launcher's [docs/specs/spec-06-mcp-protocol-and-work-orders.md:105] (proposed placement in `aieos launch`).
- **A gone session's record** (specification 5 point 10, which leaves the form of these calls to this text) [docs/specs/spec-05-adapter-contract.md:125]: when a session's lease is gone before its record is written (a violation's release, an expiry, a crash), the core writes that session's observed read-set record as its own observation, with no fencing token, at the launcher's end after a violation or an expiry, or at the next start of the same task before that start runs the core's expiry (proposed: this order at every start: the gone sessions' records, then the expiry, then the Resume Check, then the grant).
- **After a crash**, a leftover lease row stays until it has expired and the launcher's next start runs the expiry, or until the crashed session is ended by the core outside any runtime session, which releases its leases (`aieos end`, section 3) [docs/specs/spec-05-adapter-contract.md:119].
- **The base's limits**, which specification 5 leaves for this launcher to close [docs/specs/spec-05-adapter-contract.md:121]: that the base given is the base branch's tip, that the root and its Git state are untouched by the change, and a check 0 of the contract against the approved one. Check 0 is closed for the launcher: every start builds the Resume Check's inputs at HEAD, with the contract at HEAD and the approved contract's hash, and the Resume Check gives an error when they differ [src/aieos_bootstrap/resume_check.py:529-530]; the hook makes no check 0 and needs none (revision 5). The base-tip check is closed by the launcher's start (proposed, revision 5): `start` and `launch_outside` take a `base` argument, the name of the base branch, with the default `main`, checked with the other arguments: a `base` out of form gives "refused" with the reason "argument", before the gone sessions' records and the expiry. In a step "base", right after the step "head" and before the step "log" (the gone sessions' records and the expiry run before it, as now), the launcher reads the local ref `refs/heads/<base>` once through `gitread`, in the form `["rev-parse","--verify","--end-of-options","refs/heads/<base>"]`, where `<base>` is 1 to 100 characters, using only ASCII letters, digits, ".", "_", "-" and "/"; split on "/", every part is non-empty, begins with a letter or a digit and does not end in "." or ".lock"; and ".." occurs nowhere. This rule is stricter than git's; a name that git still refuses gives "refused" with the reason "base". The answer must be 40 lowercase hexadecimal characters. A ref that cannot be read, or an answer out of form, gives "refused" with the reason "base"; a HEAD that does not equal the ref's answer gives "not granted" with the reason "base"; for the starting session there is no session row, no lease, no `adapter.start` and no end. `aieos launch` takes no base option in revision 5 and passes the default `main`; an option for other bases is open (section 10 item 7). The remote-tracking ref is not read, since the launcher fetches nothing. The untouched-root check is stated here (proposed, revision 7; DEF-0101): in a step "root", right after the step "base" and before the step "log", the launcher reads the root's Git state once through `gitread`, in one fixed form, `["status","--porcelain=v1","-z","--no-renames","--untracked-files=all","--ignore-submodules=all","--",".",":(exclude).aieos"]`, where `.aieos` is the writer's `STATE_DIR`, written as a constant; the options `--no-renames`, `--untracked-files=all` and `--ignore-submodules=all` override the repository's `status.renames`, `status.showUntrackedFiles` and submodule settings, so every entry has one path. ## 7. The handoff file

- The `handoff` tool records a handoff as claim records at once and writes no file; the file is written after the submission or the session's end, which the launcher makes (DEF-0095) [docs/Deferred/DEF-0095-the-handoff-file-of-the-claim-tools-for-the-launcher.md:12].
- The core writes it after the submission or the end, from the session's `handoff` claim records, in specification 2 section 5.2's form [docs/specs/spec-02-aieos-file-format.md:116], with `commit` when the session submitted one [docs/specs/spec-06-mcp-protocol-and-work-orders.md:69]; none when the session made no `handoff` call (proposed). How the file reaches Git (which tree, who commits it, how it stays out of the agent's commit) is stated in the state-file rule below (proposed; revision 6); specification 6 left it open [docs/specs/spec-06-mcp-protocol-and-work-orders.md:97]; section 10. Built so far (revision 3; TASK-094): launcher.launch_outside writes the file after an end that gave "done", with commit None, since the command makes no submission; the shipped command, having no runtime starter, writes none in a real session; the write after a submission is built by TASK-111 (revision 9; until it lands, the write after a submission stays open, DEF-0095).
- "The last handoff" of a task for its next Work Order [docs/specs/spec-06-mcp-protocol-and-work-orders.md:60] (proposed; revision 6, replacing revision 5's "the newest by the order of its claim records in the event log"): among the sessions whose handoff file is present at the base, the one whose handoff claim records are the newest in the event log's order. A session with handoff claims and no file is not counted. With two or more files the reader chooses by that order and, when the session of every file has a handoff claim, gives no finding for them (revision 6, built by TASK-108); a claim counts only when its `refers_to` starts with `handoffs/<task>-<session>.md#`; with no file it gives none, and one file is returned whether or not the log holds a claim of its session. Revision 7 states what TASK-108 built beyond that: the files are looked for in the state directory's `handoffs/` and in `docs/handoffs/`, a session part out of form and one name present in both folders are findings, and with two or more files a file whose session has no handoff claim in the log cannot be ordered, which is a finding ("which is the last cannot be told") with nothing read (a stated choice, fail closed).
- **When a handoff file is written** (proposed; revision 6), by the way the session ended:
  - the launcher's "done" end: written, with `commit` None; built (TASK-094);
  - after a submission: written by the launcher with `commit` the submitted commit id [docs/specs/spec-02-aieos-file-format.md:116-118], once per session (the writer is create-only); built by TASK-111 (revision 9; until it lands, not built, DEF-0095): the launcher passes the fencing token of its grant, and the commit is found in the event log read for the file: the `task.submitted` events of the task that carry that token and are not compensating; exactly one, with a commit id in form, gives that commit; none gives `commit` null with no finding; more than one, an event repeated under one event id with other content, or a commit out of form gives `commit` null and a finding; a compensating `task.submitted` (recovery's) is never matched; a commit with no usable `AIEOS-Fence` trailer leaves no event with the grant's token, so `commit` is null; a log line that cannot be read as a JSON object, or that repeats a key, gives `commit` null and a finding; the file is written only after a done end of the launcher (a refused or failed end writes none, as the list below says), and the end of a session that submitted takes the "gone" path (as the code reads; TASK-111's composed-path test shows it) because the submission released the lease first, so that session's observed read-set record is the core's record for a gone session, with the reason "lease gone (released or expired)" [src/aieos_bootstrap/read_set_record.py:216], although a submission is not among the gone cases that section 5 names; that stays open (proposed; DEF-0095);
  - `aieos end` of a crashed session (section 3): none written; the core ends that session outside any runtime and holds no end report of its own;
  - an expiry, a violation's release, a refused or failed end, and the fallbacks of section 5: none written;
  - a session that made no `handoff` call: none written (revision 5).
  For the cases with no file the session's handoff claim records stay in the event log, and the limit is stated: a handoff made in a session that ended abnormally is never "the last handoff" of this section.
- **The state-file rule: files the core writes into the project-state directory outside an agent's session, the contracts under `tasks/` by `aieos import` and `aieos run` and the handoffs under `handoffs/`** (proposed; revision 6; DEF-0105 link 1 and DEF-0095):
  - Where: the core writes them into the owner's main checkout, the launcher's root, never into an agent's work tree. The launcher's check that the root is clean at the grant (section 5, revision 7) leaves the project-state directory out of its count, since these are the files the core itself writes.
  - When they count: the readers of section 6 read only the base commit, so a file counts once it is committed on the base branch whose tip the launcher requires (section 5, revision 5). An uncommitted contract is not read; a launch needs its contract committed.
  - Who commits: not the core. The core writes through its one writer (INV-004) and runs no `git add` or `git commit`: the core writes files only to the project-state directory and its logs (constitution INV-001 [docs/pre-genesis/constitution.md:29]), and a commit writes into `.git/`, outside it; and `gitread.py` holds only read-only subcommands (section 10 item 8). The commit of the state paths is made by the user, or on the self-build by the owner or by an executor script that the decision agent approved, as a commit limited to those paths on the base branch (a state commit). Automating it is a later task: a git write form in `gitread.py` and in the workflow's pattern rule, its own decision under DM A66, and the constitution's own route for the INV-001 clause; none is made or needed by this text.
  - How they stay out of an agent's commit: the agent's work tree is cut from the base after the state commit, so the files are in the base and not among its changes; CI's rule on a task's own commits refuses any changed path under `.aieos/` [.github/workflows/aieos-checks.yml:1746-1747]; and a task contract's write set does not list the state directory (proposed rule; no check reads this rule yet, so it is stated and not enforced). Limit: CI judges the pushed task range, so a local agent that wrote there is caught at the push, not at the write.
- **The event log and the other folders of the project-state directory** (proposed; revision 10; DEF-0105 link 1; specification 2 section 3). The rule above is extended to every kind of file the core writes there. By kind: (a) `events.jsonl`, the event log: committed. (b) `tasks/` and `handoffs/`: as above, unchanged. (c) `intent/` and its five folders, `changes/`, `plan/`, `genesis/`, `conformance/`: the core writes no file there yet; when it does, the same rule applies (committed in a state commit); empty folders have nothing for Git to track. (d) `local/` (the lease and read store): never committed, kept out of Git by the line `.aieos/local/` in the repository's root `.gitignore` (placed by TASK-113, a task of the self-build, not by the core; specification 2 section 3 names the user as its writer and never the core; DEF-0030). (e) `project.yaml` and `constitution.yaml`: written by no shipped command; by an approved change, outside this text. Where the state commit goes: on the base branch, pushed to main in a push of its own before any of a task's commits is pushed, with no `AIEOS-Task` trailer. G0 detect then finds no task and the deterministic rule stops [.github/workflows/aieos-checks.yml:296-299, :1736]. A state commit pushed together with a task's commits is among that push's commits outside main and is refused by the INV-004 rule [.github/workflows/aieos-checks.yml:1746-1747]. This is read from the workflow's text, not tested. CI's contract path (revision 11; the workflow's revision 18, TASK-114): G0 detect reads a task's contract at `docs/tasks/<task>.yaml` or at the project-state directory's `tasks/<task>.yaml` [.github/workflows/aieos-checks.yml:303-326, :751-774]. The contract commit must be on main, have one parent equal to the contract's base_commit, and change only the contract file, except that a contract in the project-state directory may share its commit with the event log (`events.jsonl`); the same task id added in both folders is a failure. Limits, stated: a state commit holding two contracts or any third path is refused as a contract commit; detect does not check that the event-log change only appends; a task's own commits that change the project-state directory stay refused by the INV-004 rule. This widens what G0 accepts, and the workflow's header says so (revision 18). A committed log goes to GitHub with the normal push, and what is pushed stays public permanently; it holds grants, approvals and session ids, and no secret is to be written there; the push's secret scan covers it. Nothing makes the state commit automatic or enforces it: automating it stays the later task of the bullet above (a git write form, the workflow's pattern rule, the constitution's route for INV-001).
