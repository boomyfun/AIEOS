## 2. The zero-friction principle

- The risk the concept names first: a one-line README fix that must pass through every artifact makes people remove the tool [AIEOS-concept.md:787]. The principle: "user nói ý định, AIEOS tự sinh các artifact; user chỉ duyệt khi risk đòi hỏi" [AIEOS-concept.md:789].
- "Fast path không phải bypass path": a low-risk task still has V0 (scope) and V1 (deterministic), is still written to the event log and stays traceable; only the human procedure is cut, never the control [AIEOS-concept.md:804].
- **The core runs no model.** The AIEOS core decides, grants, checks and records; it writes no code and runs no model (constitution INV-001) [docs/pre-genesis/constitution.md:27-28], from the concept's "Nó không viết code, không chạy model" [AIEOS-concept.md:162]. This is a rule, not a choice of this text; it changes only through the constitution's own route.
- **Who makes the artifacts** (proposed; reading of the decision agent, D-2238): the artifacts an intent needs are drafted by an agent working under a pulled task, where the launcher fixes the task and the agent pulls its Work Order through MCP [docs/specs/spec-06-mcp-protocol-and-work-orders.md:13], or written by the user; AIEOS checks them, records them and routes them for approval by risk. This reading reconciles the concept's own lines: "AIEOS tự sinh các artifact" [AIEOS-concept.md:789] and "AIEOS đề xuất" [AIEOS-concept.md:796] with the core that runs no model [AIEOS-concept.md:162], and with the drafting the concept gives to an AI ("AI quét repo, đề xuất") [AIEOS-concept.md:928] (decision D-2243). The dispatch, the agent pulling its own work, is the owner's answer to DM A43 Q6, "6 b" [docs/pre-genesis/decision-matrix.md:104], kept by decision D-2050 [docs/specs/spec-06-mcp-protocol-and-work-orders.md:95]; the owner may change the dispatch in one sentence. Listed in section 10 point 1.
- **Its cost, stated:** under this reading a larger intent's proposal set is drafted in a launched agent session, and each session needs the owner's launch (section 5), so `aieos run` for a larger intent does not finish in one step; the owner may raise this (section 9).

## 3. The commands

One entry point, the bootstrap's CLI (proposed: a module of the bootstrap package run as a command; its installed name and how the owner starts it on the machine are not fixed here). Every command writes, where it writes, through the core's one writer [docs/specs/spec-02-aieos-file-format.md:45]; agents act through the protocol or the CLI, never by writing the project-state directory [docs/specs/spec-01-state-and-event-model.md:51].

- **`aieos init`** [AIEOS-concept.md:939]: creates the project-state layout of specification 2 section 3 [docs/specs/spec-02-aieos-file-format.md:25], a layout settled as the owner's, with `changes/` and `local/` (DM B7 note; A59, A60, F16) [docs/pre-genesis/decision-matrix.md:158]; it writes no constitution proposal: specification 2 names no file for one (its section 4.3 form is a change request), and `aieos import` drafts the proposals (revision 3; TASK-095). Running it on the self-build raises where the interim documents under `docs/plan/` and `docs/specs/` move, which specification 2 leaves open [docs/specs/spec-02-aieos-file-format.md:275]; open in section 10.
- **`aieos import`** [AIEOS-concept.md:928], [AIEOS-concept.md:939]: makes a task whose Work Order asks an agent to read the repository and draft the architecture and constitution proposals (proposed; the reading of section 2). Approving a constitution follows the constitution's own rule: it changes only through an approved change request, and the agent only proposes; for gov-AIEOS, while the A41 delegation is in force, the decision agent approves it in the owner's place, within the limits of CR-002 parts 4 and 8 [docs/pre-genesis/constitution.md:144]; once bound, an article changes only by a genesis amendment [docs/pre-genesis/constitution.md:145]. For a product project, the user approves ("human duyệt" [AIEOS-concept.md:928]); for a user who has chosen option "b", the AI approving in their place does, with the acts the user keeps (CR-002 part 9 points 3, 4 and 8) [docs/pre-genesis/CR-002-concept-errata.md:113-114] [docs/pre-genesis/CR-002-concept-errata.md:117-118].
- **`aieos run "<intent>"`** [AIEOS-concept.md:940], [AIEOS-concept.md:792-798]: records the intent (proposed), as a `claim` record that changes no task state and approves nothing (specification 1 §12 and specification 2's revision 11, both revised with this one; section 10). An intent has no changed paths, so the risk rules cannot class it: they class a change by the highest class among the rules that match its changed paths, and a path no rule matches gets no class and is never low [docs/specs/risk-rules-gov-aieos.md:16-17]. The core alone cannot class a bare intent, and it cannot draft a write-set from one, since that would take a model (section 2). So (proposed) a task contract is made from a task-contract template (not yet written): its write-set is given by the user or drafted by an agent under a pulled task (section 2); the core only fills the template's fixed fields, classes the contract by its write-set and records it. It classes under the rules read at the base [docs/specs/risk-rules-gov-aieos.md:18] (for gov-AIEOS that file; for a product project the risk rules of its own `project.yaml` [docs/specs/spec-02-aieos-file-format.md:29]); a declared risk lower than the rules give is not used [docs/specs/risk-rules-gov-aieos.md:19]. A task classed low still needs its contract approved before a lease (section 4) [docs/specs/spec-01-state-and-event-model.md:65], and still goes through V0, V1 and the event log [AIEOS-concept.md:804]. Otherwise (a class other than low, or no class), or when the intent needs more than one task, it makes a drafting task whose output is the proposal set of [AIEOS-concept.md:796] (requirement, specifications, tasks, risk and verification plan), routed to the approval flow (section 4).
- **`aieos status`** [AIEOS-concept.md:800-801]: progress, drift, tasks waiting for approval, requirements lacking assurance; each read from an existing reader of specifications 1, 3 and 4, and shown as "not available" where no reader exists yet (proposed). The MCP tool `status` of specification 6 serves the agent in a session; the command serves the user, from the same core reads (proposed).
- **`aieos tasks`** (proposed; added, not named at concept :997): the core function `list_tasks` (decision D-2040 C1) [docs/specs/spec-06-mcp-protocol-and-work-orders.md:14]: the tasks that may be taken. Fixed by sources: a task is READY only once approved with every dependency DONE [docs/specs/spec-01-state-and-event-model.md:65], and a lease is granted only on a task in READY or REWORK, one per task [docs/specs/spec-01-state-and-event-model.md:78]. Proposed: no live lease on the task, and its output form.
- **`aieos end <session>`** (proposed; added, not named at concept :997): ends a crashed session from outside any runtime session and outside the runtime's tool calls, which releases its leases, as specification 5 leaves to "specification 7's CLI" [docs/specs/spec-05-adapter-contract.md:119].
- **Outside any runtime** (proposed): `aieos end` and `aieos launch` refuse when the environment holds a session id or a project root, so that they are not run from an agent's shell inside a launched session; the limit for a determined agent stays as specification 5 states it (a nested runtime with a session id and a root it chooses) [docs/specs/spec-05-adapter-contract.md:120].
- **`aieos launch <task>`** (proposed; added, not named at concept :997): the launcher (section 5). Running it starts a runtime session with the MCP server connected; connecting the MCP server to the runtime is a Claude Code setting, and launching it and any act at a permission prompt are the owner's [docs/specs/spec-06-mcp-protocol-and-work-orders.md:88], which DM A51 item (4) keeps with the owner [docs/pre-genesis/decision-matrix.md:112]. So the owner runs it, or the machine asks the owner's permission; it is never run by any task without the owner's approval, since a task that carries out such an act is approved by the owner (CR-002 part 4 limit 5) [docs/plan/master-plan.md:70]. As shipped (revision 3; TASK-094), `aieos launch` has no runtime starter: inside a runtime it refuses, and otherwise it refuses with no runtime starter and starts nothing; the composition a launch would run, launcher.launch_outside, is in the core and is tested with stand-ins only. For TASK-094 only, the owner answered "có" (decision D-3154), so the decision agent approved and accepted that task in the owner's place; a real starter, and any run of the command with one, stays the owner's act and is asked separately.

## 4. The approval flow

- The concept's form: "[Approve] [Edit] [Reject]", then "chạy tự động tới khi cần escalate" [AIEOS-concept.md:797-798]. An approval is an authority record, one per task, bound to the task contract's hash (A42) [docs/pre-genesis/decision-matrix.md:103] [docs/specs/spec-01-state-and-event-model.md:93]; each answer is recorded as specification 1 §12 sets it (revision 3): Reject as an `authority` record with the same binding and `outcome` `fail`, never counted as an approval, Edit as a `claim` record holding the note, neither adding a task state; Edit returns the item to its drafter with the user's note (proposed).
- Who may approve what is not changed here. For gov-AIEOS in v0.1, until the governor exists, each task is accepted by one approval of the decision agent, except where CR-002 part 4 limits 5 or 8 make the owner the approver [docs/plan/master-plan.md:93]. For a product project that has not chosen option "b", A35 holds: the project starts at L1 and a person approves every task [docs/pre-genesis/CR-002-concept-errata.md:111]; with option "b", the AI approving in the user's place does, as section 3 says. The approval record of a requirement or a specification in the proposal set has no rule yet (A42 covers tasks): open (section 10). "auto-accept" [AIEOS-concept.md:793] is the concept's goal; nothing here raises an autonomy level or changes who accepts; any later change is its own decision.
- DEF-0020's option-b documents wait for, among others, the approval flow of M7 [docs/plan/master-plan.md:139]; they are outside gov-AIEOS's scope and are named here, not placed.

## 5. The launcher

- **Requirements**, carried in full from specification 5 [docs/specs/spec-05-adapter-contract.md:112] (and as specification 6 relies on them [docs/specs/spec-06-mcp-protocol-and-work-orders.md:26-27]): the session's start, submission and end are made outside the runtime session they govern, never by the agent's tool calls; each run of the runtime has a session id of its own, made by the launcher; the core's expiry runs before a grant; the runtime is not started without a grant, and a start without a grant is ended at once; on a grant the session id, the project root and the base are passed in the runtime's environment (the base as `AIEOS_BASE`, the base branch's tip at the grant, `main` for the self-build, written as 40 lowercase hexadecimal characters; that part proposed in specification 5); the observed read-set record is written before the lease is released, except as specification 5's point 10 says; the session is ended in every case. (Specification 5's revision 5 note on `AIEOS_BASE`: [docs/specs/spec-05-adapter-contract.md:138].) With them, specification 5 revision 6's stated limit at the same line: the core's end can refuse before any release, and the launcher built with TASK-094 falls back to the outside end after "argument" or "record", or directly when the contract's write set cannot be read or the granted answer is out of form with a session id that is a string, a granted answer whose session id is not a string ending nothing, leaving such a session and other refused or failed ends to `aieos end` or the lease's expiry (revision 3).
- **The Resume Check** runs before every grant: only CONTINUE and CONTINUE_WITH let the lease be granted [docs/specs/spec-03-resume-check-and-decision-engine.md:13], and the Work Order is issued only after them [docs/specs/spec-06-mcp-protocol-and-work-orders.md:51] [docs/plan/master-plan.md:79]; at a new session's start on a task still IN_PROGRESS under a lease it holds, the check is the launcher's [docs/specs/spec-06-mcp-protocol-and-work-orders.md:105] (proposed placement in `aieos launch`).
- **A gone session's record** (specification 5 point 10, which leaves the form of these calls to this text) [docs/specs/spec-05-adapter-contract.md:125]: when a session's lease is gone before its record is written (a violation's release, an expiry, a crash), the core writes that session's observed read-set record as its own observation, with no fencing token, at the launcher's end after a violation or an expiry, or at the next start of the same task before that start runs the core's expiry (proposed: this order at every start: the gone sessions' records, then the expiry, then the Resume Check, then the grant).
- **After a crash**, a leftover lease row stays until it has expired and the launcher's next start runs the expiry, or until the crashed session is ended by the core outside any runtime session, which releases its leases (`aieos end`, section 3) [docs/specs/spec-05-adapter-contract.md:119].
- **The base's limits**, which specification 5 leaves for this launcher to close [docs/specs/spec-05-adapter-contract.md:121]: that the base given is the base branch's tip, that the root and its Git state are untouched by the change, and a check 0 of the contract against the approved one. Check 0 is closed for the launcher: every start builds the Resume Check's inputs at HEAD, with the contract at HEAD and the approved contract's hash, and the Resume Check gives an error when they differ [src/aieos_bootstrap/resume_check.py:529-530]; the hook makes no check 0 and needs none (revision 5). The base-tip check is closed by the launcher's start (proposed, revision 5): `start` and `launch_outside` take a `base` argument, the name of the base branch, with the default `main`, checked with the other arguments: a `base` out of form gives "refused" with the reason "argument", before the gone sessions' records and the expiry. In a step "base", right after the step "head" and before the step "log" (the gone sessions' records and the expiry run before it, as now), the launcher reads the local ref `refs/heads/<base>` once through `gitread`, in the form `["rev-parse","--verify","--end-of-options","refs/heads/<base>"]`, where `<base>` is 1 to 100 characters, using only ASCII letters, digits, ".", "_", "-" and "/"; split on "/", every part is non-empty, begins with a letter or a digit and does not end in "." or ".lock"; and ".." occurs nowhere. This rule is stricter than git's; a name that git still refuses gives "refused" with the reason "base". The answer must be 40 lowercase hexadecimal characters. A ref that cannot be read, or an answer out of form, gives "refused" with the reason "base"; a HEAD that does not equal the ref's answer gives "not granted" with the reason "base"; for the starting session there is no session row, no lease, no `adapter.start` and no end. `aieos launch` takes no base option in revision 5 and passes the default `main`; an option for other bases is open (section 10 item 7). The remote-tracking ref is not read, since the launcher fetches nothing. That the root and its Git state are untouched by the change stays open (DEF-0101). The launcher built with TASK-094 starts with max_risk None, so it grants nothing until a measured tier backs a declaration, and reads the contract's write set at the grant's head; until the task that builds the base-tip check (TASK-106) it closes no base limit (DEF-0101) (revision 5).
- **Owner acts, described and never performed** by this text or by any task without the owner: starting the runtime with the MCP server connected (running `aieos launch`), since connecting the MCP server to the runtime is a Claude Code settings change and an act at the owner's permission prompt; placing hooks; changing settings. DM A51 item (4) keeps settings, hooks and acts at a permission prompt with the owner [docs/pre-genesis/decision-matrix.md:112]; a task that carries out such an act is approved by the owner (CR-002 part 4 limit 5) [docs/plan/master-plan.md:70].
- T4 Headless, "CLI/SDK tự động", "Như T3 + điều phối tự động" [AIEOS-concept.md:653]: out of v0.1 (proposed). So the concept's "chạy tự động tới khi cần escalate" [AIEOS-concept.md:798] holds in v0.1 only inside a launched session: each session needs the owner's launch, and no session starts the next one.

## 6. The readers of the Work Order's inputs at the base

- `get_work_order` returns the Work Order compiled at the base, again at each call, so the same object only while the task's last `task.approved` and last `decision.execution` stay the same [docs/specs/spec-06-mcp-protocol-and-work-orders.md:54]; `query` reads only at the base [docs/specs/spec-06-mcp-protocol-and-work-orders.md:102]. Their readers need the launcher's base (decision D-2171) [docs/plan/m6-exit-review.md:20].
- This text carries the readers (decision D-2239, choice A): the core reads each input file at the commit `AIEOS_BASE` (proposed: through `git` run as a process, standard library only). Under INV-001 the core starts a process only through one wrapper with a pinned list of allowed executables [docs/pre-genesis/constitution.md:29], that wrapper is `src/aieos_bootstrap/gitread.py`, whose pinned list is `git` with four read-only subcommands in fixed forms, an object id being 40 or 64 lowercase hexadecimal characters [src/aieos_bootstrap/gitread.py:4-15]. A file is read at the base by a tree walk with those forms (`cat-file -p` of the commit, then of each tree, then of the blob), as `scope_reconcile.read_base` does for its two fixed files through its tree walk (`_blob_at`) [src/aieos_bootstrap/scope_reconcile.py:233-243] (proposed: reuse that walk for any path). A further form would be a change to that module and to the workflow's pattern rule, each under its own decision [src/aieos_bootstrap/gitread.py:14-15]; none is needed by this text. Git is trusted as the contract reader already trusts it [docs/specs/spec-05-adapter-contract.md:121]. This text changes no tool contract of specification 6; the stated choices of TASK-083's two tools (DEF-0098) are written into specification 6 revision 8 (DM F74). Any further wording change that drafting or review shows specification 6 needs is listed in section 10 as a separate later revision of specification 6, not made with this text.
- **The state directory of the readers** (proposed; revision 6; DEF-0105 link 1 and DEF-0095). The core writes a task contract to `<root>/<state dir>/tasks/<task>.yaml` and a handoff to `<root>/<state dir>/handoffs/<task>-<session>.md`, the state directory being the writer's `STATE_DIR` [src/aieos_bootstrap/writer.py:95] (specification 2 section 3). Until this revision the readers of this section read only `docs/tasks/<task>.yaml` and `docs/handoffs/<task>-*.md` [src/aieos_bootstrap/base_inputs.py:56, :452, :589-591], the self-build's hand-kept layout, so a contract written by `aieos import` or `aieos run` and a handoff written by the launcher were never read; this was found while preparing this revision (decisions D-4001, D-4002). One rule for the self-build is chosen here: a task's contract is read at the state directory first and, when it is absent there, at `docs/tasks/<task>.yaml`; the handoffs under the two folders are listed together; a contract, or a handoff file name, present in both folders gives a finding and nothing is read (fails closed). So the self-build's hand-kept `docs/` files stay readable and no file moves, a file the core writes into `.aieos/` is read once it is committed (section 7), and a reader fixed to one folder would leave the other kind unread. The reasons for not keeping `docs/` alone: moving the core's files there is a manual step in the loop, and the writer's layout is the settled one (specification 2 section 3). Limit: while the self-build holds a file of one task in both folders, that task's inputs are refused until an approved act removes one. All the readers of a task contract apply this same rule through one shared resolution (proposed), so that the Work Order, the Resume Check, the launcher and the hook read the same contract. They are: `base_inputs` at the commit [src/aieos_bootstrap/base_inputs.py:452, :677] (used by the launcher, `resume_inputs` and `resume_log_inputs`); `task_contract.read_contract` [src/aieos_bootstrap/task_contract.py:3, :246], which gives the hook's write set [src/aieos_bootstrap/claude_code_pretool_hook.py:318]; and the contract walk of the hook's shell allowlist [src/aieos_bootstrap/claude_code_shell_allow.py:6, :289] (called at claude_code_pretool_hook.py:229). The handoff listing is `base_inputs` only. No reader gains the literal `.aieos` for this rule: each takes the state directory from `writer.STATE_DIR` (the shell allowlist reader already carries it as the folder of the policy file [src/aieos_bootstrap/claude_code_shell_allow.py:58]), because CI's INV-004 string rule refuses a string naming `.aieos` in `src/` except in the writer and the shell allowlist reader [.github/workflows/aieos-checks.yml:1519-1520]; this text changes nothing under `.github/`.

## 7. The handoff file

- The `handoff` tool records a handoff as claim records at once and writes no file; the file is written after the submission or the session's end, which the launcher makes (DEF-0095) [docs/Deferred/DEF-0095-the-handoff-file-of-the-claim-tools-for-the-launcher.md:12].
- The core writes it after the submission or the end, from the session's `handoff` claim records, in specification 2 section 5.2's form [docs/specs/spec-02-aieos-file-format.md:116], with `commit` when the session submitted one [docs/specs/spec-06-mcp-protocol-and-work-orders.md:69]; none when the session made no `handoff` call (proposed). How the file reaches Git (which tree, who commits it, how it stays out of the agent's commit) is stated in the state-file rule below (proposed; revision 6); specification 6 left it open [docs/specs/spec-06-mcp-protocol-and-work-orders.md:97]; section 10. Built so far (revision 3; TASK-094): launcher.launch_outside writes the file after an end that gave "done", with commit None, since the command makes no submission; the shipped command, having no runtime starter, writes none in a real session; the write after a submission stays open (DEF-0095).
- "The last handoff" of a task for its next Work Order [docs/specs/spec-06-mcp-protocol-and-work-orders.md:60] (proposed; revision 6, replacing revision 5's "the newest by the order of its claim records in the event log"): among the sessions whose handoff file is present at the base, the one whose handoff claim records are the newest in the event log's order. A session with handoff claims and no file is not counted. With two or more files the reader chooses by that order and gives no finding, replacing the finding that `base_inputs` gives today ("which is the last is open") [src/aieos_bootstrap/base_inputs.py:595-597]; with no file it gives none.
- **When a handoff file is written** (proposed; revision 6), by the way the session ended:
  - the launcher's "done" end: written, with `commit` None; built (TASK-094);
  - after a submission: written by the launcher with `commit` the submitted commit id [docs/specs/spec-02-aieos-file-format.md:116-118], once per session (the writer is create-only); not built (DEF-0095's task);
  - `aieos end` of a crashed session (section 3): none written; the core ends that session outside any runtime and holds no end report of its own;
  - an expiry, a violation's release, a refused or failed end, and the fallbacks of section 5: none written;
  - a session that made no `handoff` call: none written (revision 5).
  For the cases with no file the session's handoff claim records stay in the event log, and the limit is stated: a handoff made in a session that ended abnormally is never "the last handoff" of this section.
- **The state-file rule: files the core writes into the project-state directory outside an agent's session, the contracts under `tasks/` by `aieos import` and `aieos run` and the handoffs under `handoffs/`** (proposed; revision 6; DEF-0105 link 1 and DEF-0095):
  - Where: the core writes them into the owner's main checkout, the launcher's root, never into an agent's work tree. That the root is untouched stays open (DEF-0101; section 5).
  - When they count: the readers of section 6 read only the base commit, so a file counts once it is committed on the base branch whose tip the launcher requires (section 5, revision 5). An uncommitted contract is not read; a launch needs its contract committed.
  - Who commits: not the core. The core writes through its one writer (INV-004) and runs no `git add` or `git commit`: the core writes files only to the project-state directory and its logs (constitution INV-001 [docs/pre-genesis/constitution.md:29]), and a commit writes into `.git/`, outside it; and `gitread.py` holds four read-only subcommands (section 10 item 8). The commit of the state paths is made by the user, or on the self-build by the owner or by an executor script that the decision agent approved, as a commit limited to those paths on the base branch (a state commit). Automating it is a later task: a git write form in `gitread.py` and in the workflow's pattern rule, its own decision under DM A66, and the constitution's own route for the INV-001 clause; none is made or needed by this text.
  - How they stay out of an agent's commit: the agent's work tree is cut from the base after the state commit, so the files are in the base and not among its changes; CI's rule on a task's own commits refuses any changed path under `.aieos/` [.github/workflows/aieos-checks.yml:1693-1694]; and a task contract's write set does not list the state directory (proposed rule; no check reads this rule yet, so it is stated and not enforced). Limit: CI judges the pushed task range, so a local agent that wrote there is caught at the push, not at the write.
