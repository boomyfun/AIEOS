## 1. Purpose and scope

- It fixes three file kinds that CM names but does not format: the executable fixture of a scenario (CM §2, last point), the frozen set file (CM §4) and the run record (CM §4). It also fixes the governor entry point and, from revision 3, the Resume Check entry point that the runner calls (section 9), and, from revision 6, the Risk Engine entry (section 10), and, from revision 10, the Capability Boundaries entry (section 11), and how a run compares observed with expected results, no wider than CM §3.
- It changes no scenario, no expected result and no rule of CM. Approving a scenario stays as CM §5 says; freezing a fixture is a separate approval (section 7).
- Not in scope: the content of any fixture; the runner's, the governor's and the Resume Check's code (Master Plan §4 M2 and M3); the CI workflow (the owner's: A61; constitution SEC-003).
- Not covered by these files: a fixture of section 4 gives the inputs of GS §3.2 as values, so how the governor derives them from the task contract, the requirements, the policy and the constitution is not tested by a conformance run; an acceptance that rests on such a run lists it as not covered (GS §6.2). The Risk Engine fixture of section 10 runs the derivation for RISK-01 only (revision 6).

## 2. Files, paths and the canonical form

- `tests/conformance/set.py`: the frozen set file (section 3). `tests/conformance/fixtures/<module name>.py`: one fixture file per realised scenario (section 4), the module name being the scenario id in lowercase with `-` replaced by `_` (for `ACC-01`, `acc_01`). The Resume Check fixture files of section 9 are `tests/conformance/fixtures_rc/<module name>.py` instead, the module name formed the same way (for `RC-01`, `rc_01`) (revision 4), and the Risk Engine fixture file of section 10 is `tests/conformance/fixtures_risk/<module name>.py` (for `RISK-01`, `risk_01`) (revision 6), and the Capability Boundaries fixture file of section 11 is `tests/conformance/fixtures_cb/<module name>.py` (for `ADV-02`, `adv_02`) (revision 10). These paths are proposed; a run record is the runner's output in the CI channel, not a file of the repository (section 6).
- The fixture files and the set file are scenario files in the sense of constitution GOV-002 (section 8), and they are "code" in the sense of Master Plan §8, so a task that adds them needs an approved contract and the relay of its start.
- CM §2 lists repositories, commits and records as fixture material. A fixture realises the repository and commits only as values of the evaluation request (commit ids, changed paths) and as records; no repository is built (proposed).
- Canonical form, for the JSON text of every file of this document (proposed): JSON (RFC 8259) in UTF-8 without a byte-order mark; LF line ends; object keys sorted by Unicode code point; an indent of two spaces, one key or list item per line; an empty list written `[]` and an empty object `{}`; `true`, `false` and `null` allowed; integers only, no fractions or exponents; in strings, only `"` and `\` are escaped with a backslash, and control characters as `\u` with four lowercase hex digits; one final LF. The run record is such a text; each file of sections 3 and 4 wraps one (next point). A JSON text not in this form makes its file malformed (section 6). A file's identity is the SHA-256 of its bytes.
- The file kind of sections 3 and 4 (revision 2; proposed): each such file is a Python module whose bytes are exactly the first part `DATA = r'''`, then a JSON text in the canonical form of the previous point, unchanged, then the last part `'''` and one LF: one assignment of the JSON text, byte-exact, to one name, in a raw triple-quoted string. A JSON text that contains `'''` cannot be wrapped, and its file is malformed. The runner and the tests never import or execute these modules: they read the file's bytes (not with the name `open`, which the CI channel refuses under `src/` and `tests/`), check both fixed parts byte-exact, and parse and check the JSON text between them. A file's identity stays the SHA-256 of the module file's bytes, and freeze approvals bind that hash (section 7). The reason: the CI channel's tool part of constitution INV-002 admits only Python source under `src/` and `tests/` (the article's pinned list of data file types, kept with the checker, is empty). No check is exempted: the CI channel's checks for OPS-003, SEC-001, SEC-002, static security analysis and deterministic_rule all run over these files. When the files move to `.aieos/conformance/`, each is unwrapped into a new file with its own freeze approval; whether a later revision of the CI workflow pins `.json` under `tests/conformance/` instead is the owner's (A61; constitution SEC-003).

## 3. The frozen set file

| Key | Value |
|---|---|
| `scenario_set_version` | the version of the bound set the file realises: `2` |
| `scenario_set_file_hash` | the SHA-256 of the set's file at that version, as Genesis charter version 2 §2 binds it |
| `fixture_set_version` | this file's own version: `1` for the first frozen set, one more at each later freeze (proposed) |
| `scenarios` | one entry for each of the 32 scenarios of the set, in the order of the set's rows (the order of charter version 2 §5): `{id, row_hash, capability, fixture}`, where `row_hash` is the SHA-256 of the scenario's row line without its line end (decision D-115 C1's method; charter version 2 §5), `capability` is one of `Verification`, `Resume Check`, `Risk Engine` and `Capability Boundaries` (the set's section 1), and `fixture` is `{path, sha256}` of its fixture file, with `path` relative to the repository root and written with `/`, or `null` |

- The file holds the whole bound set. In M2 a fixture is written for each of the 19 scenarios of the Verification capability (ACC-01 to ACC-17, ADV-01, ADV-03); one that cannot be realised faithfully gets `null` (section 5). The other 13 have `null` and are `NOT_RUN` until their milestones (Master Plan §4 M2, exit; CM §3). In M3 a fixture is written for each of the 11 Resume Check scenarios (RC-01 to RC-11; section 9). In M4 a fixture is written for RISK-01 (section 10). In M5 a fixture is written for ADV-02 (section 11).

## 4. The fixture file

| Key | Value |
|---|---|
| `scenario`, `row_hash` | the scenario's id and row hash, equal to its set-file entry |
| `cases` | a list of cases, one per task the scenario's Given names (one for every scenario except ACC-13, which names three) (proposed) |

Each case (proposed structure):

| Key | Value |
|---|---|
| `request` | the evaluation request of spec 2 §6.5 |
| `inputs` | the inputs of GS §3.2, one object: `traces_to` (a list of entity ids), `risk` (`low`, `medium`, `high` or `critical`), `owner_kept_act`, `weakens_evidence`, `delegation_in_force` and `auto_accept` (each `true` or `false`; `auto_accept` for the task's risk class), `verification_plan` (a list of gate ids), `evidence_profile` (a list of `{dimension, evidence_types}`), `applicable_articles` (a list of `{id, evidence_required}`, the latter a list of evidence types as the constitution gives them), `policy_version`, `level_version` and `ruleset_version` (strings) (proposed spelling and forms of GS's inputs) |
| `records` | the records the governor reads, each in the form of spec 2 §6.2 |
| `when` | `evaluate` (acceptance is evaluated; `request.task_state` is `VERIFYING`) or `re_evaluate` (after a record is written; `request.task_state` is `IN_REVIEW`; GS §5, "Leaving IN_REVIEW"); a `when` that does not agree with `request.task_state` makes the fixture malformed |
| `expected` | `decision`: a list of decision values; `next_state`: a list of task states; `missing`: the complete list of `{dimension, evidence_type}` pairs reported missing (empty when none is); `reverify`: a list of record ids; `approval`: `null`, or `{record_id, source_class}` of the approval record that must be cited; `ai_approval_shown`: `true` when the decision must show that the acceptance rests on an AI approval, `false` when it must show that it does not; `not_fixed`: the names of the other keys of `expected` that the scenario does not fix |

- Every key of `expected` other than `not_fixed` is present with a value or named in `not_fixed`, never both; a fixture that breaks this is malformed.
- The key names of `expected` are this document's; section 6 says which field of the decision record each is read from. Expected values use only the concept's and the DM's terms: the decision values of concept lines 299-303, task states, dimensions, evidence types and source classes. No expected value uses a name that a later specification defines (CM §2).

## 5. Faithfulness

- A fixture realises exactly one scenario and names its id and row hash.
- `expected` comes only from the scenario's own Expected cell, read with its Source cell. Nothing in GS, in another specification or in the governor's behaviour supplies an expected value: an element the Expected cell does not fix is named in `not_fixed` and is not compared (CM §2, "not fixed").
- The Given comes from the scenario's Given cell and the set's section 1 defaults; where the task's risk is high or critical (ACC-16, ACC-17), its profile is that of `assurance-model.md` §5. Values that none of these fix (identifiers, hashes, times) are placeholders of their spec 2 form, and no expected element depends on them.
- A scenario that no fixture can realise faithfully gets no fixture: its set-file entry is `null` and it is `NOT_RUN`. It is never re-expected, narrowed or replaced to make a fixture possible (CM §5; CR-002 part 4 limit 8).

## 6. The run, the governor entry point and the comparison

- The runner calls one governor function per case with the case's `request`, `inputs` and `records`, and receives one acceptance decision record in the form of spec 2 §6.4 (proposed: the function `evaluate` of the module `aieos_bootstrap.governor`, both taken from the base, GS §4 rule 1). Where spec 2 §6.4 names `rests_on_ai` but not its form, the decision record gives it as `{entries, approval}`: `entries` the `{dimension, evidence_type}` pairs that rest only on AI review, and `approval` `true` exactly when the cited approval record is a delegated approval of the decision agent (GS §6.2) (proposed).
- Each key of `expected` is read from the decision record as follows: `decision` from `decision`; `next_state` from `next_task_state`; `missing` from the `missing_types` of each entry of `profile_used`, with that entry's `dimension`; `reverify` from `reverify`; `approval` from `approval_record`, whose `source_class` is read from the case's records; `ai_approval_shown` from `rests_on_ai.approval`.
- A case passes only if every key not in `not_fixed` is observed: the observed decision and next state are in their lists; the observed missing pairs equal the expected list as a set; every expected `reverify` id is in the observed list; the cited approval record and its source class equal `approval`; and the observed `rests_on_ai.approval` equals `ai_approval_shown`. No decision outside the expected list is emitted (CM §3). The comparison is on these values, never on wording.
- A scenario is `FAIL` if any of its cases fails. Otherwise it is `NOT_RUN`, never a pass, if its set-file entry is `null`; its fixture is missing or malformed; its fixture's hash differs from the set file; its row hash differs from the row in the bound scenario file read from the base; the entry point is absent; or a call raises or returns a record that is not a decision record. Otherwise it is `PASS` (CM §3).
- A run does not count, and every scenario of it is `NOT_RUN`, if the set file is missing or malformed, its hash differs from the hash its freeze approval binds (section 7), or its `scenario_set_file_hash` differs from the bound scenario file (CM §5: "Until approved, no acceptance may rest on the set").
- The run record (CM §4) is a file in the canonical form with these keys (proposed): `set_file_sha256`, `scenario_set_version`, `fixture_set_version`, `runner` (`{path, sha256}` of the runner's module at the base), `governor_identity` (GS §2), `commit` (the evaluated commit), `counts` (`true` or `false`, as the previous point says) and `results` (one `{id, result}` per scenario, in the set file's order, `result` being `PASS`, `FAIL` or `NOT_RUN`). It is recorded as one record of spec 2 §6.2 with only that section's keys: `fact_kind` `observation`, `source_class` `deterministic_tool_external_ci`, `recorder` the runner's `path` and `sha256`, `subject` the evaluated task, `evidence_type` `conformance_run` and `dimension` `functional` (proposed), `outcome` `pass` exactly when the run counts and every scenario with a fixture is `PASS`, otherwise `fail`, `commit`, and `refers_to` the run-record file's SHA-256. Only a run in the CI channel can count (CM §6; A19 (5)); its effect is advisory (CM §9).

## 7. Freezing a fixture

- Adding a fixture is a `normal_cr` with a fixture-freeze approval on its hash (DM B1, B10). For gov-AIEOS the decision agent gives these approvals in the owner's place (B10 note; A51).
- They are given in the decision that accepts the task that adds the fixtures, as separate elements before the acceptance itself: one per fixture file, bound to its SHA-256, and one for the set file, bound to its SHA-256. Each is an `authority` record of spec 2 §6.2 in the task's records file (`docs/records/<task>.jsonl`; decision D-188 C5), with `approval_binding` `{kind: change_request, hash}`, the hash being the frozen file's SHA-256 (proposed: spec 2 §6.2 gives this kind for a change request's content hash, and B10 makes adding a scenario a `normal_cr`); one DM section F row lists the set file's hash and names the decision that lists the fixture hashes.
- A set file's freeze before its task (revision 5): the set file's freeze approval may instead be given in a decision of its own, before the first commit of the task that adds that set file, only when all of these hold: (a) each fixture entry the new set file names is, for that entry's scenario id and capability, the path that sections 2, 9 and 10 expect and the SHA-256 of that file's current frozen version, bound by its own fixture-freeze approval; every other byte of the new set file follows from the frozen set file it replaces, with `fixture_set_version` one more than that file's (section 3); and a script checks all of this, its output and the new set file's SHA-256 being recorded in the approving decision; (b) the approval, in the form of the previous point, is recorded in that task's records file and lands on `main` before the task's first commit, with its DM section F row, which lists the set file's hash and names the approving decision; (c) the decision that accepts the task cites it as the set file's freeze, and if the set file at the acceptance has other bytes, that decision needs a new freeze approval of them under the previous point, with the same `fixture_set_version`. Such an approval binds only its hash: it approves no fixture, scenario, task or acceptance, and the acceptance needs every other element it needs under the previous point (proposed).
- A fixture's next version frozen before its task (revision 8): a fixture file's freeze approval may instead be given in a decision of its own, before the first commit of the task that writes that file's next version, for one value of one file only: `values.risk_rules` of RISK-01's fixture `tests/conformance/fixtures_risk/risk_01.py`, which section 10 states as the risk rules policy's rules (no other value, such as `policy_version`, `articles`, `owner_kept_rules` or the profiles, and no file under `tests/conformance/fixtures/` or `fixtures_rc/` is open to this route), and only when all of these hold: (a) the new file replaces the frozen file at the same path, and every byte other than that value is as in the frozen version, every case's `expected` and `request` included; (b) that value equals section 3 of the policy as the same task will write it, that text being given in full in the approving decision; the policy's change is approved in its own right under the policy's section 6, it lowers no class and weakens no evidence requirement, and a change that would do either is the owner's and cannot use this route; (c) a script checks (a) and (b) and that no rule of the new value matches a changed path of the fixture (section 10's Given), and its output, its own SHA-256 and the new file's SHA-256 are recorded in the approving decision; (d) the approval, in the form of the second point of this section, is recorded in that task's records file and lands on `main` before the task's first commit, with its DM section F row, which lists the file's hash and names the approving decision; (e) the decision that accepts the task cites it as that fixture's freeze, and if the file or the policy at the acceptance has other bytes than the approving decision gives, that decision needs a new freeze approval of them under the second point. A set file that names such a next version may then be frozen under the previous point, its condition (a) reading, for that entry, the SHA-256 that this route's approving decision records in place of the file's current frozen version, checked by the set file's script. Such an approval binds only its hash: it approves no scenario, set file, policy, task or acceptance, and the next point applies to it unchanged (proposed).
- A frozen file changes only by a new freeze approval on its new hash (proposed). A change that makes a fixture's `expected` accept something its frozen version rejects (a wider decision or state list, a missing pair removed, a key moved to `not_fixed`, a class removed from `risk_not` or a pair removed from `profile_excludes`), so that a record counts or a task is accepted where the frozen version does not, weakens evidence requirements and is the owner's; so is removing a fixture whose expected result is that a record does not count or a task is not accepted (CM §5, applied to fixtures; CR-002 part 4 limit 8) (proposed).

## 8. Fixture tasks and the constitution

- The task type `fixture` (proposed; it settles specification 2 §10 point 5 for this one value) is a task whose every changed path is either a file of sections 2 to 4 under `tests/conformance/`, or a test module `test_conformance_*.py` directly under `tests/unit/`, `tests/integration/` or `tests/property/`, the folders whose tests the CI channel runs, that checks only those files against this document and the bound scenario file. A fixture task may also change, and only in the same task, and the same commit, as a fixture file or the set file it writes under an approval of section 7: (i) a test module directly under `tests/unit/`, `tests/integration/` or `tests/property/` whose only changes replace a pinned value of such a file (its SHA-256, the set file's `fixture_set_version`, the record id of the freeze approval that binds it, or the rule ids its values mirror), each with one exact new value equal to that of the file the task writes, and the text of docstrings and comments that only name the replaced value or its approval (no doctest and no string that code reads), as a script over the base and the task's commit shows, its output and its own SHA-256 recorded in the decision that accepts the task; and (ii) the risk rules policy (`docs/specs/risk-rules-gov-aieos.md`), only to the whole file whose SHA-256 a decision approved before the task, when the route of the previous section for a fixture's next version is used. A task with any other changed path is not a fixture task.
- A fixture task is neither an implementation nor a refactoring task, so GOV-002, whose applicability is those two types, does not apply to it, as the constitution writes it. For every other article whose applicability names implementation, a fixture task is treated as an implementation task (proposed; stricter than the constitution's text). GOV-002 has no `evidence_required` (its check is deterministic), so its not applying adds and removes no entry of the task's evidence profile (GS §3.2, applicable articles), and every other article applies as it would to an implementation task: no evidence requirement narrows (CR-002 part 4 limit 8; GS §3.2, weakens evidence).
- GOV-003 applies: A29 counts fixtures and scenarios in the evaluator, so a fixture task changes the evaluator.
- The fixture files and the set file are scenario files: `tests/conformance/**`, and `.aieos/conformance/**` once it exists, are in the forbidden set of every `implementation` and `refactoring` task (constitution GOV-002; concept line 445).

## 9. The Resume Check fixtures and entry (revision 3)

- Scope: the 11 scenarios of the set's capability `Resume Check` (RC-01 to RC-11; the set's section 4, with its Resume Check defaults in section 1), for milestone M3 (Master Plan §4 M3). "S3" is `docs/specs/spec-03-resume-check-and-decision-engine.md` revision 4 (DM F23). Sections 2, 3, 5, 7 and 8 apply to these fixtures unchanged; this section replaces sections 4 and 6 for them only.
- Which entry: the runner reads a scenario's `capability` from its set-file entry; `Verification` runs the governor entry (section 6), `Resume Check` runs the Resume Check entry below, `Risk Engine` runs the entry of section 10 (revision 6), `Capability Boundaries` runs the entry of section 11 (revision 10), and any other capability is `NOT_RUN` until its milestone (proposed).
- Where the files are (revision 4; proposed): each Resume Check fixture file is `tests/conformance/fixtures_rc/<module name>.py` (section 2), and the `path` of a Resume Check scenario's set-file entry names that folder. The runner chooses the path it expects by the entry's `capability`, which must equal the capability the bound scenario file gives that id: `tests/conformance/fixtures/` for `Verification`, `tests/conformance/fixtures_rc/` for `Resume Check`; a scenario whose entry names another capability than the bound file, or another path than the one expected for its capability, is `NOT_RUN`. The task that adds the Resume Check entry implements this, and the path of a Verification fixture does not change.
- The fixture file: `scenario`, `row_hash` and `cases` as in section 4; each case holds `inputs`, `when` and `expected` (proposed structure):

| Key | Value |
|---|---|
| `inputs` | the inputs of S3 §1 as values, one object (proposed spelling): `task_id`; `log_seq` (the sequence number of the last event read, S3 §9; a placeholder that only the record's ids use); `task_state` (`READY`, `REWORK` or `IN_PROGRESS`); `contract` (the task contract in the form of spec 2 §5.1, with at least `input_state` (`base_commit`, `depends_on`, `intent_versions`), `write_set`, `read_set`, `constitution`, `task_type`, `risk` and `autonomy.budgets`); `contract_hash` (the content hash of the contract file, spec 2 §2); `approved_contract_hash` (the hash the task's latest `task.approved` carries; S3 §2, the precondition); `head_commit`; `base_is_ancestor` (`true` or `false`); `commits` (the commits of `base_commit..HEAD`: `{id, paths, submitted}`, `paths` a list of `{path, change}` with `change` one of `added`, `modified`, `deleted`, and `submitted` `true` when a `task.submitted` event of this task names the commit); `components` and `interfaces` (spec 2 §4.2); `symbols` (for each interface entry of the read-set: `{interface, base, head}`, each the fixed form of S3 §5 or `null` when the symbol is in no file, and `ambiguous` when it is in more than one); `schemas` (for each schema entry: `{name, base, head}`, each `{path, sha256}` or `null`, or `ambiguous`); `derived_read_set` and `observed_read_set` (lists of path entries; `observed_read_set` `null` when the runtime records none); `intent_current` (for each entity of `intent_versions`: its current version, or `null` when it is missing at HEAD); `dependencies` (for each task of `depends_on`: `{state, stale_evidence}`, `state` a task state of spec 1, or `null` when the log does not know it); `articles` (the constitution's articles: `{id, scope, applicability, violated}`, `violated` `true`, `false` or `null` when no result exists); `runtime` (`{adapter, max_risk}`, `max_risk` `null` when the runtime has no declaration); `risk_rules` and `policy_version` (the policy's rules in the form of spec 2 §7); `budget_use` (for each budget of `autonomy.budgets`: `{used, reported}`; for `retries`, the count of spec 1 §5.1) |
| `when` | `resume` (the Resume Check runs, S3 §1) |
| `expected` | `decision`: a list of exactly one A15 decision value, the one the scenario's Expected cell names (each of RC-01 to RC-11 names one); `not_fixed`: always `[]`. A fixture whose list holds any other value, or more or fewer than one, is malformed |

- Not inputs: the commits' parents, the base branch's name and the module roots, since `commits` gives each commit's paths against its first parent and HEAD and the derived read-set are given as values.
- Faithfulness (section 5, applied): `expected.decision` comes only from the scenario's own Expected cell; the Given comes from its Given cell and the Resume Check defaults; values none of these fix are placeholders of their spec 2 form, and no expected element depends on them. Where a scenario names the declared read-set (RC-02 to RC-06), `derived_read_set` and `observed_read_set` are given so that they do not meet `Δ` (S3 §7, the note before its table). RC-03's "the conflict cannot be resolved automatically" is no input: S3 §6 gives STOP: scope invalid for every non-empty `Δ ∩ write-set`, and its commits are not `submitted`. RC-10 gives `budget_use` for `retries` over the contract's retries limit (S3 §2 check 8; §12 point 11), and the fixture states it.
- Placeholders that keep the other checks from firing (so that the scenario's own Given decides): `approved_contract_hash` equals `contract_hash`; `base_is_ancestor` is `true`; `intent_current` equals `contract.input_state.intent_versions` for every entity (RC-06 apart); `contract.risk`, and the class of every rule of `risk_rules` whose pattern meets a `write_set.paths` pattern, are at most `runtime.max_risk`, and every `write_set.paths` pattern is met by at least one rule (RC-09 apart); every interface and schema entry resolves at both commits (not `null`, not `ambiguous`), and, where the scenario needs `Δ` to miss it, lies outside `Δ`; every dependency is `DONE` (RC-07 and RC-11 as their Givens say); no article is `violated` (RC-08 apart) or without a result where it applies; every budget's use is under its limit (RC-10 apart).
- The entry and the comparison: the runner calls one Resume Check function per case with the case's `inputs` and receives one execution decision record in the form of S3 §9 (proposed: the function `check` of the module `aieos_bootstrap.resume_check`, both taken from the base, as for the governor). A case passes only if the observed `decision` is in `expected.decision`; the comparison is on that value, never on wording. A scenario is `FAIL` if any case fails; otherwise it is `NOT_RUN` under the conditions of section 6 with "the entry point" read as this entry and "a decision record" as an execution decision record, and also when the record carries `error` (S3 §7); otherwise `PASS` (CM §3).
