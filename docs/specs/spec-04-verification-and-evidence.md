## 1. Scope and reading order

- Specification 4 is the fourth of the seven technical specifications of concept §18: "Gate pipeline, evidence profile, quy tắc độc lập, mapping AC ↔ test" [AIEOS-concept.md:994]. Its v0.1 items are "Verification V0–V2, evidence gắn SHA, evidence profile mặc định theo risk (low/medium)" [AIEOS-concept.md:947], "Reconciliation deterministic (constitution, scope, stale evidence)" [AIEOS-concept.md:948] and "Risk rule-based, autonomy L1–L2" [AIEOS-concept.md:949]. Master Plan §4 M4 places them in the bootstrap (decision D-251).
- What already binds this area, and stays where it is:
  - the assurance model's principle: "The model is `fact_kind × source_class × evidence requirement`" [docs/pre-genesis/assurance-model.md:10], and that "Having evidence is not being authorized to accept" [docs/pre-genesis/assurance-model.md:12];
  - the governor specification, whose scope is the acceptance decision [docs/pre-genesis/governor-spec.md:11] and which says it "covers the acceptance table and parts of §18 spec 4 (evidence profile, independence rule; concept line 994)" [docs/pre-genesis/governor-spec.md:14].
- So this specification adds only what those texts leave open: how the gates V0 to V2 are run and recorded, how evidence is bound to a commit and found stale, how a task's profile is computed, how independence is stated in a record, how acceptance criteria map to evidence, deterministic reconciliation, the use of the risk rules, and autonomy as a product feature (sections 2 to 9); then the records and boundaries (sections 10 to 12) (proposed).
- Reading order: the assurance model, then the governor specification, then specifications 1 to 3, then this one (proposed).

## 2. The gate pipeline

- The concept's verification hierarchy: "V0  Diff validation        scope, forbidden paths" [AIEOS-concept.md:715], "V1  Deterministic          build, lint, typecheck, tests, constitution (deterministic)" [AIEOS-concept.md:716], "V2  Static analysis        security scanner, dependency rules, secret scan" [AIEOS-concept.md:717]; the cheap and certain run first, the costly and subjective later, "**chỉ khi risk yêu cầu**" [AIEOS-concept.md:724]. V3 to V6 [AIEOS-concept.md:718-721] are not v0.1's gates; V3 (AI review) and V5 (human review) are evidence types of a profile, not gates (section 4) (proposed).
- Where they run is bound: "**Chosen: option 1**" [docs/pre-genesis/assurance-model.md:106], V0 and V1 "run in external CI on the evaluated commit" [docs/pre-genesis/assurance-model.md:104]. V2 runs in the same channel (proposed), since the CI channel already runs the secret scan and the security scanner.
- The mapping to the governor's gates (the contract's `verification_plan`, specification 2 §5.1) (proposed):

| Gate | Concept layer | The CI steps that produce its records (workflow revision 7) |
|---|---|---|
| G0 scope | V0 | G0 task detection; G0 scope (V0) |
| G1 build | V1 | G1 build |
| G2 tests | V1 | unit_test, integration_test, property_test |
| G3 constitution | V1 and V2 | deterministic_rule, OPS-003 pattern rules, GOV-003 evaluator paths, SEC-001 secret scan, SEC-002 pattern rules, SEC-003 record, OPS-002 owner-kept paths, INV-010 replay, static_security_analysis |

- How a gate's result counts is the governor's, not this specification's: its rows decide "in the A36 order" [docs/pre-genesis/governor-spec.md:101], and a gate without a current passing result gives INSUFFICIENT_EVIDENCE [docs/pre-genesis/governor-spec.md:107].
- The governor's input names the evaluated commit and the changed paths: "`task_id`, `task_content_hash`, `evaluated_commit`, `intent_versions`, `task_state` (a state name), `changed_paths`, `retry_count` (`{used, limit}`)" [docs/specs/spec-02-aieos-file-format.md:193]. Each gate record names that same commit (section 3).
- "Dependency rules" for a standard-library-only bootstrap: no dependency file may be added, which applies INV-002's file rule to the bootstrap's tree [docs/pre-genesis/constitution.md:32-34]; no CI step carries it yet (proposed; plan o2).
- The table's step names are those of the CI workflow at revision 7; the workflow is not a source this specification cites by line, so the table is illustrative and a task that builds a gate checks it against the workflow at its base (proposed). Lint has no step of its own; the concept's example "G4 ai_review(cross-model)" [AIEOS-concept.md:466] is not a gate here, since the governor reads cross-model review as a profile entry (section 4). Which layer `deterministic_rule` belongs to stays the assurance model's open point [docs/pre-genesis/assurance-model.md:78], and which path rules report as G0 (out of scope, forbidden path) and which as G3 is an open point (section 12).

## 3. Evidence bound to a commit; stale evidence

- The rule: "Evidence luôn gắn **commit SHA** và **intent version**." [AIEOS-concept.md:728], and it is made "do **AIEOS/CI/tool/human** tạo ra, không do agent tự viết" [AIEOS-concept.md:729]. The constitution binds it: "evidence counts only when bound to the evaluated commit SHA and the current intent version; stale evidence never satisfies an entry" [docs/pre-genesis/constitution.md:58].
- The record fields that carry the binding are specification 2's: `commit`, `intent_versions` "what it is bound to (concept line 728)" [docs/specs/spec-02-aieos-file-format.md:153]; and the record's source class [docs/specs/spec-02-aieos-file-format.md:147].
- Stale evidence is a drift of kind Evidence: "Code đổi, evidence cũ thành stale" [AIEOS-concept.md:746], found deterministically by SHA [AIEOS-concept.md:746]. This specification reads "stale" as (proposed; plan o3):
  1. a record whose `commit` is not the reference commit is stale: at an evaluation the reference is the governor's `evaluated_commit`; when reconciliation runs for a DONE task it is the task's accepted commit, not the base's head;
  2. a record whose `intent_versions` differ from the current version of each intent artefact the record concerns, read at the base's head, is stale;
  3. reconciliation only: when a later commit on the base changes a path in the task's effective read-set (specification 3 §4), leaving out the commits that the task's own `task.submitted` events name, as check 1 does [docs/specs/spec-03-resume-check-and-decision-engine.md:40], every record of the task bound to an earlier commit is reported stale. This is stricter than the Resume Check, which tells breaking from non-breaking changes; it schedules a re-verify and blocks nothing, and a DONE task stays DONE [docs/specs/spec-01-state-and-event-model.md:88]. Where the read-set is an estimate, the rule inherits its flags, and a check it could not complete is listed as uncovered, never as passed.
- Rules 1 and 2 are the governor's rule 2 [docs/pre-genesis/governor-spec.md:78], cited, not changed: the governor counts no record they find. Rule 3 does not change how the governor counts a record; whether the governor should also treat such records as stale is an open point for the governor specification's revision (section 12). Finding stale evidence is a pure computation over the records and the commits read from Git, with no model call (INV-001); its result is a list of stale record ids, each with its `reason` [docs/specs/spec-02-aieos-file-format.md:180]: `commit` for rules 1 and 3, `intent_version` for rule 2 (proposed).
- The core's own refusal records keep their binding: a refused submission is an observation with `outcome` `fail` that "does not block the task" [docs/specs/spec-02-aieos-file-format.md:161].

## 4. Evidence profiles

- A profile names, per dimension, the evidence types required; acceptance checks "**từng chiều đủ hay thiếu**, không cộng điểm" [AIEOS-concept.md:687]. The defaults by risk are the concept's table [AIEOS-concept.md:701-704], bound for gov-AIEOS by the assurance model: the "**v0.1 defaults**" [docs/pre-genesis/assurance-model.md:78] for low and medium, and the "**High and critical defaults, for gov-AIEOS.**" [docs/pre-genesis/assurance-model.md:81]. This specification does not restate them (plan o1).
- How a task's profile is computed is the governor's input: "per dimension, the evidence types required: the risk default, with the differences each traced requirement declares" [docs/pre-genesis/governor-spec.md:47], where the risk is "the highest risk the policy's risk rules give for the changed paths" [docs/pre-genesis/governor-spec.md:42], and the applicable articles' "`evidence_required` joins the profile" [docs/pre-genesis/governor-spec.md:48].
- What this specification adds (proposed):
  1. **One computation, one result.** The profile is computed by one pure function from the contract, the traced requirements, the risk rules at the base and the constitution at the base, and written as one record of the task, an audit copy that every reviewer reads and that can be re-derived. The governor computes its own profile from its own inputs [docs/pre-genesis/governor-spec.md:47] [docs/pre-genesis/governor-spec.md:77] and does not read this record; a difference between the two is an advisory finding, an observation that never blocks by itself (proposed). Whether the governor should read the record instead is an open point for the governor specification's revision (section 12).
  2. **Fail closed.** A dimension or type that the inputs name and no checker produces stays in the profile and stays unsatisfied (specification 2 §6.2's rule that such a type "is never satisfied" [docs/specs/spec-02-aieos-file-format.md:160]).
  3. **Union, not override.** A traced requirement may add entries; none removes an entry of the risk default or of an applicable article (an override that removes one would weaken evidence, which for gov-AIEOS is the owner's: CR-002 part 4 limit 8 [docs/pre-genesis/CR-002-concept-errata.md:64], as the governor spec's "weakens evidence" input names it [docs/pre-genesis/governor-spec.md:44]). A declared removal is not applied; it is reported as that input. This is stricter than "the differences each traced requirement declares" [docs/pre-genesis/governor-spec.md:47] and touches the governor's open point on how profiles combine [docs/pre-genesis/governor-spec.md:191]; for products other than gov-AIEOS, whether a departure from the risk default needs a specific approval stays the assurance model's open point [docs/pre-genesis/assurance-model.md:130].
- For v0.1 products, only the low and medium defaults are in scope [AIEOS-concept.md:947], read from the policy's `default_profiles` key by item 1's function (specification 2 §7); gov-AIEOS uses the high and critical defaults from v0.1 as the assurance model binds. A change that matches no risk rule gets no decision, as the governor specification says (its section 4, rule 8).

## 5. The independence rule

- The concept's rule: "**Quy tắc độc lập:** evidence chỉ được tính khi **người/cái tạo ra nó độc lập với implementer**" [AIEOS-concept.md:706], and the question "Ai/cái gì kiểm tra?   → tool / model / human (không phải agent tự khai)" [AIEOS-concept.md:668].
- The source classes and which of them may satisfy an entry are bound in the assurance model's table [docs/pre-genesis/assurance-model.md:16-40]: for example `agent_declared` may block and never satisfies [docs/pre-genesis/assurance-model.md:22], and `deterministic_tool_external_ci` satisfies "yes, if the entry names it" [docs/pre-genesis/assurance-model.md:25]. For gov-AIEOS the "**way-2 review**" [docs/pre-genesis/assurance-model.md:36] and the decision agent's review [docs/pre-genesis/assurance-model.md:27] are the two bound exceptions. The constitution's INV-008 makes it an article [docs/pre-genesis/constitution.md:62-66].
- What this specification adds: how a record states its independence, so that a deterministic check can count it (proposed):
  1. every record names its `source_class` [docs/specs/spec-02-aieos-file-format.md:147] and its `recorder` [docs/specs/spec-02-aieos-file-format.md:148];
  2. a model review names `models` as "`{reviewer, implementer}`" [docs/specs/spec-02-aieos-file-format.md:156], and a check refuses it when the two are equal [docs/pre-genesis/assurance-model.md:36]; a missing `models` key makes the record unusable for the cross-model entry. Which source names the implementer's model, so that the check can also compare `implementer` with the model that made the task's commits, is an open point for specification 2's next revision (section 12);
  3. a record whose recorder is the implementer's session, the session that holds the task's lease, counts only as `agent_declared`, whatever class it names (fail closed); a record's class is checked against the channel it came through (re-fetched from CI, written by the core), not taken from its own field, since a locally written record counts at most as a claim unless it can be re-derived or re-fetched [docs/pre-genesis/assurance-model.md:70].
- Limits: independence between two Claude models is not independence of vendor; the cross-vendor class stays dormant for gov-AIEOS (assurance-model §2).

## 6. Mapping AC to test

- The concept's rule: "Mỗi AC phải map tới evidence thoả evidence profile của requirement." [AIEOS-concept.md:730]; and the question "Đáp ứng AC nào?       → mapping AC ↔ evidence" [AIEOS-concept.md:665].
- The contract already carries the two ends: `acceptance_criteria`, "a list of one-entry maps from an id to its text" [docs/specs/spec-02-aieos-file-format.md:108], and the `verification_plan`, whose `args` name the criteria a gate checks, so line 466's "G2 tests(AC1–AC3)" is "`{gate: G2, check: tests, args: [AC1, AC2, AC3]}`" [docs/specs/spec-02-aieos-file-format.md:112]. The governor reads the plan as "the gates that must pass" [docs/pre-genesis/governor-spec.md:46].
- What this specification adds (proposed):
  1. **Coverage check, deterministic.** Every AC id of the contract appears in the `args` of at least one gate of the plan; an AC that no gate names is a finding, recorded before the first evaluation as a record the governor's existing rows can read (proposed; the coverage criterion follows concept line 730). The record is written with `outcome` `blocking` and `blocking_kind` `other` [docs/specs/spec-02-aieos-file-format.md:152], which the governor's existing row 2 already reads [docs/pre-genesis/governor-spec.md:106], so an uncovered AC blocks now without a governor revision (proposed, fail closed). An uncovered AC is a defect of the contract, which the implementer cannot fix, and a NEEDS_REWORK would only use up retries before ESCALATED; so the check runs first when the contract is approved, where it writes the record for the approver to see and does not itself refuse the approval, and at an evaluation it blocks only as the fail-closed fallback (proposed). How a corrected contract clears such a record, given that the governor does not let rules 2 and 6 silence a blocking record [docs/pre-genesis/governor-spec.md:89], is a known cost and an open point (section 12). An empty `acceptance_criteria` list, and a gate `args` entry that names no AC of the contract, are findings of the same kind.
  2. **Test to AC.** A test names the ACs it stands for in its name or docstring (the concept's "test khai báo AC nó chứng minh" [AIEOS-concept.md:781]); a script lists, per AC, the tests that name it; an AC with no test is a finding for G2's criteria, written in item 1's form. The listing is evidence of mapping, not of correctness; until item 3's key exists, concept line 730 is covered at gate and test level only.
  3. **Records.** A gate record names the ACs it covers in a new key (an open point for specification 2's next revision; `refers_to` does not take AC ids).
- Limits: a name-based mapping shows that a test claims an AC, not that it tests it; whether a test is weaker than its criterion stays with review (the way-2 briefs already ask it).

## 7. Reconciliation, deterministic

- The concept's drift kinds and how each is found [AIEOS-concept.md:742-749]; v0.1 takes the three deterministic ones: "Reconciliation deterministic (constitution, scope, stale evidence)" [AIEOS-concept.md:948]. Every drift goes "**DETECT → CLASSIFY → PROPOSE**" [AIEOS-concept.md:756].
- The events are specification 1's [docs/specs/spec-01-state-and-event-model.md:81-90], written in specification 2's forms [docs/specs/spec-02-aieos-file-format.md:163-183]: `evidence.stale`, whose effect is that a "re-verify is scheduled; execution is not blocked; a DONE task stays DONE with stale evidence" [docs/specs/spec-01-state-and-event-model.md:88], and `violation.detected` and `drift.detected` [docs/specs/spec-01-state-and-event-model.md:86-87].
- What this specification adds (proposed):
  1. **Constitution drift:** after a commit reaches the base, the deterministic rules of every article whose scope meets the commit's changed paths are run (the CI's G3 steps are those rules); a failed rule on the base is a `violation.detected` with the article's id in `refers_to`; its subject is the commit, no task's state changes, and it is handled as a record by the decision agent or the owner (proposed). A G3 failure at a task's evaluation and the same failure found later on the base are one finding, not two.
  2. **Scope drift:** the concept's "Commit sửa file không thuộc task nào" [AIEOS-concept.md:745]. Specification 2 requires the trailer only where "A commit made under a lease carries `AIEOS-Task: <task id>`" [docs/specs/spec-02-aieos-file-format.md:197]; it says nothing of other commits. So (proposed): a base commit with no `AIEOS-Task` trailer, or with a trailer whose contract (the version the task's lease named) does not hold a changed path, is detected. A detected commit is not a claim when all its changed paths lie in a list of non-task paths that the approved policy at the base names; never by its message or trailer alone. A commit that touches the constitution, the policy, the evaluator paths or `.github/` is always a claim. Every other detected commit is a `drift.detected` claim, which changes no state [docs/specs/spec-01-state-and-event-model.md:86] and is closed by an authority record (for example a decision that names the commit), made by whoever may make it: the decision agent under A51, and the owner for a commit that carries out or changes an act A51 item (4) keeps. The non-task list does not exist yet; adding it is a change to the policy (critical_cr) and an open point (section 12). Until it exists, the self-build's records, decision, contract and workflow commits are each a claim, closed by the decision that made them. A merge commit is read by its changes against its first parent, as specification 3 reads commits.
  3. **Stale evidence:** section 3's rules 2 and 3, run at the same point (rule 1 applies at an evaluation only); each base commit gives at most one `evidence.stale` event per task and reason, with the list of the stale record ids that no earlier `evidence.stale` event of the same task and reason has listed [docs/specs/spec-02-aieos-file-format.md:180], idempotent by an event id derived from the task, the commit and the reason (proposed, as the writer derives refusal ids).
  4. **Where it runs** (plan o4): in the CI channel as evidence, and in the core when a task is submitted, as the governor's input; the core's caller is the item carried in DEF-0030 (D-415 C3). All three are pure computations; their events are appended only through the single writer (INV-004).
- Limits: architecture, semantic and orphan drift [AIEOS-concept.md:747-749] are partial and need AI or heuristics; they are not v0.1's (proposed).

## 8. Risk, rule-based

- The concept: risk decides what follows [AIEOS-concept.md:578-586], and the MVP is rule-based [AIEOS-concept.md:591-592]. For gov-AIEOS the rules are the approved policy (risk-rules-gov-aieos.md, DM F15): "A change's class is the highest class among the rules that match any of its changed paths" [docs/specs/risk-rules-gov-aieos.md:16], and a change with an unmatched path "gets no class" and "is never low" [docs/specs/risk-rules-gov-aieos.md:17]; rules are read "from the base or a pinned ref, never from the change they classify" [docs/specs/risk-rules-gov-aieos.md:18].
- This specification sets no rule and changes no class (the policy is its own approved document; changes to it are critical_cr). It adds only (proposed): the classification is one pure function over the changed paths, and the other facts the policy's rules name, and the policy at the base; its result is written as one record of the task, an audit copy that every reviewer reads; section 4's function calls this function and does not read the record. The governor computes its own risk [docs/pre-genesis/governor-spec.md:42] and does not read the record; a difference between the two is an advisory finding that never blocks by itself, and whether the governor should read the record is an open point (section 12). A change with an unmatched path, or one that a rule cannot be evaluated for (for example a component tag or a `touches` fact that nothing provides), gets no class and is never low [docs/specs/risk-rules-gov-aieos.md:17]. The policy's machine-readable form at the base is an open point (section 12). RISK-01 (fail-closed classification) becomes runnable when that function exists (plan o5).

## 9. Autonomy L1 to L2

- The concept: an agent is autonomous until one condition breaks [AIEOS-concept.md:606-612]; levels L0 to L4 [AIEOS-concept.md:618-624]. For gov-AIEOS the bound rule: "the AIEOS self-build stays at L1" [docs/pre-genesis/assurance-model.md:90], and `auto_accept` "is expressible only for a risk class raised to L2 or above" [docs/pre-genesis/assurance-model.md:94]; the constitution's INV-011 [docs/pre-genesis/constitution.md:77-81].
- This specification describes L1 and L2 as a product feature only (proposed): a level is read from the approved policy; L2 allows auto-accept only where the policy says so and the governor's row 4 applies [docs/pre-genesis/governor-spec.md:108], and the bounds of the assurance model's section 6 apply unchanged [docs/pre-genesis/assurance-model.md:90-97]: L2 is "Auto-accept task ≤ medium risk khi đủ assurance" [AIEOS-concept.md:622]; a level is raised only on metrics [AIEOS-concept.md:626] and a change request; `auto_accept` cannot be expressed while C13 is not PASS [docs/pre-genesis/assurance-model.md:97]. The escalation when a condition breaks [AIEOS-concept.md:613-616] is specification 5's runtime and specification 3's decisions, not this one's. For gov-AIEOS nothing here raises a level; L2 while P-CRED or C13 is not PASS stays the owner's, as the master plan lists [docs/plan/master-plan.md:119] (plan o6).

## 10. The verification record and the governor's inputs

- What the governor reads is bound: its records [docs/pre-genesis/governor-spec.md:55-74] and its decision record [docs/pre-genesis/governor-spec.md:131-161]; the decision contract is specification 2's [docs/specs/spec-02-aieos-file-format.md:184-190].
- This specification adds (proposed) the records its own computations write, all in specification 2 §6.2's form: the task's profile (section 4), its risk class (section 8), the AC coverage finding (section 6), the stale-record list and the reconciliation events (sections 3 and 7). Each is written once per evaluated commit, except the AC coverage finding, which is written once per contract version, through the core's single writer (INV-004 [docs/pre-genesis/constitution.md:42-46]; TASK-016), with `source_class` `deterministic_tool_local` when made by the core and `deterministic_tool_external_ci` when made in the CI channel.

## 11. Boundaries

- The governor "runs no test or checker; it reads their records" [docs/pre-genesis/governor-spec.md:178]; this specification's checks produce those records and decide no acceptance.
- Specification 3 already draws the line: "Evidence profiles, gates and stale evidence are specification 4's" [docs/specs/spec-03-resume-check-and-decision-engine.md:163], and the acceptance decision stays the governor's [docs/specs/spec-03-resume-check-and-decision-engine.md:162].
- No model call (INV-001 [docs/pre-genesis/constitution.md:27-31]); no runtime hook and no observed read-set (specification 5's); records written before AIEOS governs its own build "carry their recorder and are not authoritative" [docs/specs/spec-03-resume-check-and-decision-engine.md:165].
