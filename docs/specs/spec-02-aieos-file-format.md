## 1. Purpose and scope

- This is the second of the seven technical specifications of concept §18 (line 992): "Schema YAML/MD cho constitution, requirement, spec, ADR, task contract, handoff".
- It fixes how the project-state directory is laid out, how each entity of spec 1 §3 is written as a file or as an event, and the spelling of every name that spec 1 left to it (spec 1 §4, §5; its section 10 points 1 and 2). Within it: the task contract format (concept §7.1, lines 425-484), the field names of the decision contract (`governor-spec.md` §11 point 8; A15) and the record formats the governor reads and writes (`governor-spec.md` §3.1, §3.3, §6.1).
- Not in scope: what the risk rules say (the self-build's risk rules, the third M1 document); the Resume Check and the content of execution decisions (specification 3); evidence profiles and the gate pipeline beyond the names used here (specification 4); the adapters' own files (specification 5), except the adapter declaration's keys (section 7.1) and the observed read-set record (section 6.2), which specification 5 §11 points 3 and 4 give to this specification (revision 6). It creates no file. Only the AIEOS core writes the project-state directory (constitution INV-004), and the first code task's write-set has nothing under `.aieos/` (Master Plan §8).

## 2. General rules

- Text files are UTF-8 without a byte-order mark, with LF line ends (proposed).
- Structured entities are YAML files; prose entities are Markdown files that start with a YAML front-matter block between two `---` lines (concept line 992, "YAML/MD"; the split is proposed).
- Field names are lowercase `snake_case`, as in the concept's examples (lines 333-387, 429-470). Event types are lowercase words joined by dots, as in spec 1 §5. State names are the concept's, in capitals: DRAFT, READY, IN_PROGRESS, VERIFYING, ACCEPTED, DONE, IN_REVIEW, REWORK, ESCALATED, REJECTED, BLOCKED, STALE (lines 521-529).
- Ids follow the concept's examples: `REQ-012`, `SPEC-012.1`, `ARC-auth`, `ADR-031` (lines 403-406), `TASK-142` (line 430); constitution articles `INV-001`, `SEC-001`, `OPS-001` and the like (lines 335-356); change requests `CHG-NNN` (proposed; not `CR-`, which the concept errata use). A file is named after its id, `<id>.yaml` or `<id>.md`, except the two single files `project.yaml` and `constitution.yaml` and the handoffs (section 5.2) (proposed).
- Versions are written `v1`, `v2`, … (line 437). Every intent entity has one (line 409).
- A commit id is written in full, as Git prints it, in lowercase hex; never abbreviated (proposed).
- Hashes (all proposed): a file's content hash is the SHA-256 of its bytes, written as 64 lowercase hex digits. A contract's `contract_hash` is the content hash of its file (spec 1 §3). The `task_content_hash` of an evaluation (A42; `governor-spec.md` §3.1, proposed there) is the SHA-256 of the contract file's bytes followed by one LF and the evaluated commit id. Spec 1 §3 and §5.4 name one "contract hash"; this specification spells it as these two, because a contract is approved before any evaluated commit exists (section 6.2, `approval_binding`).
- Unknown fields are an error: a file or event with a field that this specification does not name is malformed (`governor-spec.md` §4 rules 6 and 7 treat a malformed input as not used or as giving no decision) (proposed). This applies to field names, not to the values of open vocabularies (section 6.2).

## 3. Layout (proposed; DM B7; owner point)

```text
.aieos/
├── project.yaml            # the policy: risk rules, autonomy, adapters, shell allowlist (concept line 868)
├── constitution.yaml       # concept line 869
├── intent/                 # concept lines 870-871; B7: the single intent root
│   ├── requirements/  specs/  architecture/  decisions/  conventions/
├── changes/                # change requests (proposed)
├── tasks/                  # task contracts (concept line 872)
├── handoffs/               # concept line 873
├── genesis/                # B7
├── conformance/            # B7
├── plan/                   # B7
├── events.jsonl            # the append-only event log (concept line 874); committed (proposed reading)
└── local/                  # the local store; ignored by Git, never committed (concept line 876; proposed)
```

- `intent/decisions/` holds the ADRs (concept line 871; B7). It does not hold the governor's decision records, which are records of the event log (section 6).
- The local store (leases, sessions; spec 1 §5.2) and, from revision 7, the reads kept for the read-set record (spec 1 §2) is SQLite and is never committed (concept line 876). Proposed: `.aieos/local/state.sqlite`, with `.aieos/local/` listed as ignored by Git. Its tables (proposed): `store` (`epoch`, `counter`), `leases` (`task_id`, `holder`, `session_id`, `fencing_epoch`, `fencing_counter`, `granted_at`, `expires_at`) and `sessions` (`session_id`, `holder`, `started_at`, `ended_at`); times as in section 6.1. Revision 7 adds a fourth table (proposed), `reads` (`session_id`, `task_id`, `seq`, `path`): the paths an adapter passed for a session and its task, each once, `seq` giving their first-seen order, written by the core's accumulation, which refuses unless the session holds a live lease (a check of the store's lease, not of a token the hook carries), and kept until that session's observed read-set record (section 6.2) is appended from them or found present, then removed; with no later start of that task they stay, unused (specification 5 §7 and §11 points 7 and 10); Execution State, ephemeral runtime telemetry, not authoritative (spec 1 §2), and never a record: what counts is the record written from it, which stays a lower bound. The tree above, the places and the E4 text below are unchanged, and the E4 text stays true: the reads are runtime telemetry kept in the local store.
- Only the AIEOS core writes this directory, through one writer (concept lines 858, 879; constitution INV-004).
- B7 adds `genesis/`, `conformance/` and `plan/` to the concept's tree (lines 866-877); `changes/` and `local/` are this specification's. B7 gives names only; what this section says each one holds is this specification's reading. Where the interim documents now under `docs/plan/` and `docs/specs/` move is open (section 10).
- Proposed text for CR-001 E4, for the owner (A22; CR-002 part 8), in the errata's language, aligned with the tree above: "§13.4 (dòng 865-877): cây thư mục `.aieos/` có thêm `genesis/`, `conformance/` và `plan/` (theo DM B7), `changes/` (các Change Request) và `local/` (local store của lease và session, không commit, như dòng 876)." Not asked here; it goes in this specification's approval request as an owner point (D-150 C5).

## 4. Intent files

### 4.1 Constitution: `constitution.yaml`

A top-level `version` and a list `constitution` of articles (concept lines 333-362, 375-387; constitution.md §2):

| Field | Required | Values and source |
|---|---|---|
| `id` | yes | the article id (line 335) |
| `category` | yes | `architecture`, `correctness`, `security`, `operational` (lines 336-357); for gov-AIEOS also `governance` (constitution.md §2) |
| `rule` | yes | the rule in words (line 337) |
| `source` | for gov-AIEOS | where the article comes from (constitution.md §2) |
| `check` | yes | `deterministic`, `partial` or `judgment` (lines 364-367) |
| `tool` | for `deterministic` and `partial` where a checker exists | `{type, …}`: `type` names the checker kind, and the other keys are those of that kind (proposed), for example `from` and `forbid` for `dependency_rule` and `require` and `in` for `pattern` (lines 339, 346); SEC-001 has none (lines 350-354) |
| `evidence_required` | for `partial` and `judgment` | a list of evidence types (lines 347, 360) |
| `severity` | yes | `blocking`, … (line 340) |
| `scope` | no | `{components: [component ids], paths: [...]}`; absent means project-wide, run at project time only (lines 378-380, 397) |
| `applicability` | no | `{task_types: [...]}` (lines 381-382; section 5.1, `task_type`) |
| `enforcement` | no | `{mode, checker, cost}`: `mode` is `blocking`, `warning` or `advisory`, and `cost` is `cheap`, `moderate` or `expensive` (lines 383-386) |

The bound constitution of the self-build (`docs/pre-genesis/constitution.md`) states these fields in Markdown, `source` and the `governance` category included. Writing it as `constitution.yaml` is a later task of its own (open, section 10). The keys of each `tool` type are set with that checker (open, section 10); until a type's keys are set, the unknown-field rule does not judge its other keys.

### 4.2 Requirement, specification, architecture, ADR, convention: `intent/<kind>/<id>.md`

Front matter, then the prose (concept lines 401-409):

| Kind | Front-matter fields |
|---|---|
| requirement | `id`, `version`, `title`; `evidence_profile`, by dimension, only where it differs from the risk default (lines 676-685, 697) |
| specification | `id`, `version`, `title`, `traces_to` (requirements); the body holds acceptance criteria with ids, each verifiable (line 404) |
| architecture | `id`, `version`, `title`, `components`, `interfaces`; the body holds responsibilities and boundaries (line 405) |
| ADR | `id`, `version`, `title`; the body holds the decision, the reasons and the options set aside (line 406) |
| convention | `id`, `version`, `title`; `becomes_article` when it is raised into the constitution (line 407; proposed) |

- `components` is a list of `{id, paths: [...], tags: [...]}`; `interfaces` a list of `{id, component}` (line 405; proposed). A constitution `scope.components` names component ids, and a risk rule's `component_tags` matches a change when a changed path lies under the paths of a component carrying one of those tags (lines 592, 599; section 7; proposed).
- A file carries no `status`. Whether a specification is draft, baselined or superseded (B9) is derived from its `authority` records (section 6.2), as a projection (spec 1 §6); for gov-AIEOS, a delegated approval is also recorded as a DM section F row, as F11 records spec 1's (proposed).

### 4.3 Change request: `changes/<id>.md` (proposed)

Front matter `id` (`CHG-NNN`), `targets` (entity ids with their current versions) and `new_versions`; the body says what changes and why. It carries no `status`: its approval is an `authority` record bound to its content hash (section 6.2), and its rejection an `authority` record too. Intent changes only through an approved one (line 409).

### 5.2 Handoff: `handoffs/<task id>-<session id>.md`

Front matter `task`, `session`, `commit` (the commit the session submitted, if any; proposed), then the six lists of concept line 537 as front-matter lists of strings: `done`, `not_done`, `assumptions`, `discoveries`, `risks`, `proposals` (proposed); the body holds free notes. Each item of `discoveries` and `proposals` also enters the log as one `claim` record whose `refers_to` is the handoff file and the item's place in its list (spec 1 §3; proposed), written as one string `handoffs/<task id>-<session id>.md#<list>/<n>`, `<list>` the list's key and `<n>` the item's place counted from 1 (revision 10; proposed; specification 6 §4 proposes the same form for the items of the other four lists); the file never makes them facts (line 537).

## 6. The event log: `events.jsonl`

### 6.1 Line format

One JSON object per line, in sequence order (concept line 874; spec 1 §4):

| Key | Required | Value |
|---|---|---|
| `event_id` | yes | a unique id; appending a known one has no effect (concept line 856) |
| `type` | yes | one of section 6.3 |
| `appended_at` | yes | UTC time, ISO 8601 with `Z` (proposed) |
| `seq` | yes | an integer: 1 on the first line, then one more than the previous line's (proposed) |
| `task_id` | when the event concerns a task | the task id |
| `fencing_token` | on every event that results from a lease holder's action (spec 1 §4), `task.submitted` among them | `{epoch, counter}` (spec 1 §8) |
| `corrects` | on a correction | the `event_id` it corrects (spec 1 §4) |
| `payload` | yes | an object, by type (sections 6.2 to 6.4) |

When the payload is a record whose `subject` is a task id, the envelope's `task_id` is that same id; a record about an intent entity has no `task_id` (proposed).

A record (`record.added`, and the records that sections 6.3 and 6.4 name) has the fields of `governor-spec.md` §3.3 and B5:

| `recorder` | who or what wrote it, in words (proposed) |
| `session` | for a record whose content is an agent session's own statement (a claim, or a review it made), the `session_id` of that session, spelled as the local store's `sessions` and `leases` tables spell it (section 3); the writer's statement, recorded and not checked: a session is never a source of Project State (spec 1 §3) (proposed) |

| `refers_to` | for a record about another record, an event, a change request or a handoff item: its id, for a handoff item in section 5.2's string form (revision 10); for a check observation of a constitution article, that article's id (specification 3 §2 check 6 and §12 point 8) (proposed) |

- The audit copies of specification 4 §4 item 1 and §8 (proposed):
  - The `evidence_type` names `risk_class` and `evidence_profile` are reserved for these records, which record a computed value, not a proof; for these two names this narrows the open vocabulary of the next bullet. Such a record has `fact_kind` `observation`; `source_class` `deterministic_tool_local` (made by the core) or `deterministic_tool_external_ci` (made in the CI channel) (specification 4 §10); its key (`risk_class` or `evidence_profile`); `commit` (the evaluated commit) and `intent_versions` (those of that evaluation); and no `outcome`, `gate`, `blocking_kind` or `dimension`. The key's value is `null` or, for `risk_class`, one of the four classes, and for `evidence_profile`, a list of `{dimension, evidence_types}` whose `evidence_types` is a list of names. The key's presence and form are checked; its value is the writer's statement.
  - A record under either name that breaks this form, and a record of any other type that carries `risk_class` or `evidence_profile`, is malformed, so the governor does not use it and lists it as uncovered (`governor-spec.md` §4 rule 6): one that carries `outcome` `fail` is not counted as a failure, and one that lacks `commit` or `intent_versions` is not used either; one that carries `outcome` `blocking` still blocks, with the effect its `blocking_kind` gives (rule 4: rule 6 does not silence a blocking record). The record checker applies these form rules once a task extends it; until then it refuses any record with either key, as an unknown field (section 2).
  - At this revision the governor takes no value from these keys; whether it should read these records stays open (specification 4 §12 point 10). Having no `outcome` and no `dimension`, a well-formed record satisfies no evidence entry (`governor-spec.md` §4 rule 3 needs `pass` in the entry's dimension), blocks nothing (rule 4 needs `blocking`) and is no gate result (it has no `gate`). Like any bound observation, once it is bound to an earlier commit it is listed among a decision record's re-verify records, so each later evaluation lists the earlier copies, and reconciliation may report them as stale (specification 4 §3 and §7 item 3); that changes no decision value.
  - The value is the writer's, not the governor's: the governor also uses a higher risk that the contract declares (section 5.1) and computes its own profile; a difference between the two is an advisory finding that never blocks by itself (specification 4 §4 item 1 and §8).
  - A writer writes at most one record of each of the two names per task and evaluated commit (specification 4 §10); a second one with another value is the writer's error, which no check of this specification finds (a limit).
  - The policy version that gave the value is not on the record (a limit). The `policy_version` of a `decision.acceptance` record of the same task and evaluated commit (section 6.4) is the governor's own input: it may be absent, `null` in an error decision, different between several such decisions, or not the one the writer used; it is a hint, never proof.
- The intent versions of gov-AIEOS records (revision 5; decisions D-1107 and D-1108; working record DEF-0074) (proposed):
  - The governor and the bootstrap's other modules take an entity's version only in the form `v<N>` (section 2), while a self-build contract names each entity of `input_state.intent_versions` by its file's path with the SHA-256 of its bytes. For gov-AIEOS the version of such an entity is `v<N>`, N being that document's own revision number, read from the DM row that names the file's exact SHA-256 together with "revision N" of that document. A Genesis charter gives a document's version only where the charter itself names that document's SHA-256 and its revision; a charter's own version is never a document's version.
  - The mapping fails closed: a SHA-256 that no DM row names, one that rows name with two different revisions, or a row whose text does not match the mapping's fixed pattern gives the entity no version. A record of that task then carries no version for that entity, the records file states the reason, and the governor does not read the record for it. A version is never guessed.
  - Each record of a task carries in `intent_versions` the mapped version of every entity of its contract, the entity's id being its path; the evaluation request carries the current map (section 6.5); a record bound to an older revision is stale (constitution INV-007).
  - An applicable constitution article's entry is recorded under the article's id as the record's `dimension` (the bootstrap governor joins an applicable article's `evidence_required` under a dimension named by the article's id; DEF-0074). A CI step or a review that meets several entries is written as one record per entry, each naming the SHA-256 of the same output in its `basis`, which says that the one step or review stands for the entries it names.
  - Forward only: records written before this revision (the self-build's records of TASK-001 to TASK-057) are not rewritten; the governor reads none of them, and this is a stated limit (DEF-0074), under which no missing entry is counted as met.
  - At this revision no module computes the mapping: a script of the self-build writes the mapped versions into the records it builds. A core that takes file SHA-256 values as versions itself is a later option (DEF-0074).
- The observed read-set record (revision 6; specification 5 §7 and §11 point 4) (proposed):
  - The `evidence_type` name `observed_read_set` is reserved for it, as revision 4 reserves two names; for this name this narrows the open vocabulary of the next bullet. Such a record is written by the core from what the adapter passes (specification 5 §7; INV-004). It has `fact_kind` `observation`; `source_class` `deterministic_tool_local` (specification 5 §6: a hook's record on the agent's machine is at most that class); `subject` the task id, so the envelope's `task_id` is that id (section 6.1); a `recorder` naming, in words, the adapter and the session (specification 5 §7), and, for a record written without a held lease, saying so and why (revision 7); and the key `read_paths`. It has no `session` key, no `outcome`, `gate`, `blocking_kind`, `dimension`, `commit` or `intent_versions`. How a session is identified, so that specification 3 can take "the runtime's records of the task's earlier sessions" (specification 3 §1), is specification 5 §11 point 7's.
  - `read_paths` is a list of distinct non-empty strings, written by the core as the adapter passes them, each naming a path the adapter saw read in the session; the core removes a repeated path before writing, and until point 13 sets the form, distinct means by exact string equality (case folding or normalisation set there may change it). Their form (the separator, relative or absolute paths, case, drive letters, links and junctions, normalisation) is set by the contract of specification 5 §11 point 8 and is open here (section 10 point 13); until it is set, the key's presence and the list's form are checked, and its content is the writer's statement, recorded and not checked. The list may be empty, which says only that no read was seen.
  - At most one record per task and session (specification 5 §7); a second one for the same task and session is the writer's error, which no check of this specification finds (a limit). The core's path derives the record's event id from the task and the session, so a repeat of the same pair through it has no effect or is refused (section 6.1; revision 7, proposed); the limit stays for a record written under any other id. A session that ends abnormally (a crash, an expired lease, a resume after compaction) may leave no record or a partial list, which says only what was seen; such an end is specification 5 §11 point 10's. A record under this name that breaks this form, and a record of any other type that carries `read_paths`, is malformed, so the governor does not use it and lists it as uncovered (`governor-spec.md` §4 rule 6); one that carries `outcome` `blocking` still blocks, with the effect its `blocking_kind` gives (rule 4). The record checker applies these form rules once a task extends it; until then it refuses any record with `read_paths`, as an unknown field (section 2), and accepts a record under this name without `read_paths` by its general rules only (a limit, as for revision 4's names).
  - What it shows: a lower bound at best. A read through a shell command, through a tool no hook covers, before the hook was in place, or outside what the path form can name is not in the list; a hook cannot show its own completeness or integrity, and the agent may be able to change the hook's configuration (specification 5 §6 and §7; A25); a missing record proves nothing, since a hook that does not fire neither refuses nor records (specification 5 §8). A locally written record counts at most as a claim unless it can be re-derived from Git or re-fetched from an external channel (B5): its `fact_kind` is the form specification 5 §7 gives, and B5 limits its weight, not its label. Having no `outcome` and no `dimension`, a well-formed record satisfies no evidence entry (`governor-spec.md` §4 rule 3), blocks nothing (rule 4) and is no gate result (it has no `gate`); it is not used and can be listed as uncovered (`governor-spec.md` §4 rule 6), which changes no decision value; having no `commit`, it has nothing to re-verify. Specification 3 takes the observed source only from a runtime of tier T3 or above (specification 3 §4), and no runtime's tier counts until it is measured (specification 5 §3 and §7); until then such records are kept and not used, and the read-set stays an estimate.
  - Section 6.1's `fencing_token` rule applies to the event that adds such a record unchanged; which lease the session held, the ids that tie an observation to a session and a lease, and the channel by which the adapter passes it, and whether that event is a lease holder's action, are specification 5 §11 point 7's, for the first M5 contract that writes an adapter's observations to the core. For the Claude Code adapter (revision 7, proposed; specification 5 revision 4, §11 points 7 and 10): the event is a lease holder's action, fenced by the session's token, when it is written before the lease is released; when the session's lease is already gone ('gone' as specification 5 §11 point 10 defines it: a violation's release, an expiry, a crash), the core writes the record as its own observation, with no fencing token, by its own path only, and its recorder says that it was written without a held lease, and why (an abnormal end included); those words, like every `recorder` text, are the writer's statement, recorded and not checked. Section 6.1's rule for lease holders' events is unchanged by this.
- Evidence types and dimensions are open vocabularies in v0.1: the names of concept lines 681-684 and 701-704, of B3 and of `governor-spec.md` §4 rule 3, and others that a requirement or an article names. A type is satisfied only by records that `governor-spec.md` §4 rule 3 lets satisfy it, so a type that no checker and no review counted there produces is never satisfied (fail closed; proposed).
- The core's own observations of spec 1 §7 and §8 are records with `source_class` `deterministic_tool_local` and `evidence_type` `unfenced_write` (a commit at recovery whose lease is not held) or `refused_submission` (a token or expiry refusal), `outcome` `fail` (proposed). A refused submission changes nothing (spec 1 §8), so it does not block the task; whether an unfenced write should block the task's acceptance is open (section 10).

### 7.1 The adapter declaration (revision 6; specification 5 §3 and §11 point 3) (proposed)

- Where: `adapters` in `project.yaml` is a list of declarations, one per adapter id; a declaration names one configuration, and a new runtime version, platform or settings replaces it with a declaration of the new configuration. No new file or folder is added, so the layout of section 3 is unchanged. Being in the policy, a declaration is read at the base, never from the change being judged (specification 5 §3 item 3).
- The keys of one declaration (concept lines 630-645; specification 5 §3):

| Key | Required | Value |
|---|---|---|
| `adapter` | yes | the adapter's id, lowercase ASCII words joined by hyphens, as `claude-code` and `generic-chat` (concept lines 633, 639); unique in the list; the adapter that the Resume Check's `runtime` names (specification 3 §9) |
| `tier` | yes | the target tier, `T0` to `T4` (concept lines 647-653); a target only, which gives the runtime no standing by itself (specification 5 §6) |
| `configuration` | yes | `{runtime, platform, version, settings}`, each a non-empty string: the runtime × platform × version × configuration of CR-001 E1 that the declaration is measured in, or is to be measured in (specification 5 §3 item 1); `settings` names the configuration, for example by the SHA-256 of its settings file |
| `capabilities` | yes | a map from a capability name to `true` or `false` (concept lines 634, 640); the names are an open vocabulary; an absent name is `false` |
| `assurance` | yes | `{preventive, runtime, posthoc}`, each `none`, `weak` or `strong` (concept lines 635, 641) |
| `max_risk` | yes | `low`, `medium`, `high` or `critical` (concept lines 636, 642; the risk values of section 5.1) |
| `measurement` | no | a reference to the measurement of this configuration (specification 5 §3 item 1), its form section 10 point 12's; absent while none exists |

- Reading (specification 5 §3 items 2 and 3, and its three cases):
  - A declaration with no `measurement`, or whose `measurement` resolves to no valid measurement, is read with every `assurance` field `none` and `max_risk` `low`, whatever it states (fail closed); its declared `tier` and `capabilities` then give no standing, and specification 3 counts no tier from them (specification 3 §4; specification 5 §7).
  - What makes a measurement record valid for a declaration (its form and class, that it names the same configuration, who may write it) is not set here: every measurement of an adapter's assurance is the owner's (specification 5 §10; DM C6, A30), and the record's form stays open (section 10 point 12). The owner's own check of the machine guards (C6) and of P-CRED is recorded as a measurement with the result safe, by the owner's decision, with no saved result, and the owner lifted specification 5 §11 point 14 (DM A69); how a declaration points to that measurement is part of point 12 and is not decided here. Until point 12 is settled, no `measurement` value resolves, so a declaration the core reads is read at its weakest. No module reads these keys yet, and the self-build does not yet lease tasks through the core (Master Plan M8), so this rule does not narrow A69 while that holds; point 12 is to be settled before it stops holding.
  - A runtime with no declaration in the list gives the Resume Check's `runtime.max_risk` the value `null`, so check 7 gives STOP: runtime insufficient (specification 3 §2 check 7). A malformed declaration (a required key missing, an unknown key, a value outside its set), or a list in which an `adapter` occurs twice, gives `error` and no decision.
  - The Resume Check takes from a declaration only the adapter and its `max_risk` (specification 3 §1 and §9), so nothing yet compares the running session's runtime, platform, version and settings with the declared `configuration` (a limit, for point 12).
- A declaration is policy: adding or changing one is a change to `project.yaml`, and raising any assurance or autonomy because of an adapter stays the owner's (specification 5 §10).
- This revision writes no declaration and sets no tier, assurance value or `max_risk` for gov-AIEOS's runtime (specification 5 §3, last bullet); no module reads these keys until a task adds them.

### 7.2 The shell allowlist (revision 8; specification 5 §11 points 5 and 6) (proposed)

- Where: `shell_allow` in `project.yaml` is the policy's list of allowed shell commands, a list of strings; the task contract's `capabilities.shell.allow` (section 5.1) is the task's list. Both are read at the base, never from the change being judged (specification 5 §3 item 3 and §11 point 6), the policy file by the same reader as the contract: the accepted reader walks both files from the base's object store by a copy of the contract reader's walk [src/aieos_bootstrap/claude_code_shell_allow.py:85-167, :276-303] (revision 9).
- An entry's form: words of ASCII letters, digits and the characters - _ . / : = , + only (narrower than the judge's set: no ; & | ( ), tab or newline), separated by single spaces, and not empty. Its first word has no "="; the first word's name (the part after its last "/" or ":", in lower case, a final ".exe" removed) is not a program that runs code or commands and does not end as a script; and an entry whose first word's name is git has a second word that is a subcommand, not an option and not a refused subcommand. This is the form the entry check accepted with TASK-062 gives [src/aieos_bootstrap/claude_code_hook.py:67-72, :81-86, :89-121]. At the judge, an entry holding any other character never matches [src/aieos_bootstrap/claude_code.py:45-46]; under this section the reader has already voided such a list (the next point), so the judge never sees the entry.
- Fail closed: an absent key, an unreadable `project.yaml`, a value that is not a list, or a list with any entry outside the form is read as an empty list, as a whole; the same holds for a contract's `capabilities.shell.allow` (absent is denied, line 562). One malformed entry voids its whole list, as a malformed allowlist refuses every call in the entry accepted with TASK-062 [src/aieos_bootstrap/claude_code_hook.py:135-140]; the reader passes the empty list instead, so a malformed list refuses shell calls and not every tool call; each such refused shell call with a live tied lease is a section 8 violation and ends the session (specification 5 §11 points 5 and 6). The accepted reader reads each list in a fixed form narrower than YAML, the policy's as the `  - ` items under one top-level `shell_allow:` line and the contract's as one `shell: {allow: [...]}` value of double-quoted strings; any other shape, a missing `.aieos` tree, `project.yaml` or contract file, or a blob that fails the contract reader's byte checks reads as empty [src/aieos_bootstrap/claude_code_shell_allow.py:174-194, :219-259, :276-303] (revision 9).
- Matching: the rule of the judge accepted with TASK-061 [src/aieos_bootstrap/claude_code.py:37-46, :57-59, :189-226, :250-253, :327-331]. After the judge's push and parse refusals [src/aieos_bootstrap/claude_code.py:314-326], a command text reaches the lists only if every character is in the safe set; it is split into simple commands, each a list of words; a simple command matches an entry when the entry's words are its first words, compared case-sensitively from the first word as given; the text is allowed only when every simple command matches.
- Both lists: a simple command is allowed only when it matches an entry of the policy's list and an entry of the contract's list. Two entries that both match one command are related by word prefix, so this equals matching one list: for every pair of a policy entry and a contract entry where one is a word prefix of the other, the longer of the two. The computation is the reading contract's; this revision states the rule. The accepted reader computes it [src/aieos_bootstrap/claude_code_shell_allow.py:262-273] (revision 9).
- What an entry admits: an entry whose program runs other code (a shell, an interpreter, a build tool, a script) allows everything that code does, a push that the code puts together while it runs, never shown in the command text, included [src/aieos_bootstrap/claude_code.py:50-56]. The entry check refuses only the names on its lists, which are a minimum and not complete, so an entry for a program that runs code but is not on them passes the form check [src/aieos_bootstrap/claude_code_hook.py:44-51]; such an entry is approved, as below, with that reach in view.
- Approval: this revision adds no entry. Every entry of `shell_allow` is a change to the policy, approved on its own and never as part of a task's own change; an entry that, by its command or by anything it allows, can reach the network, run `git push`, use a token or credential, spend money, publish or send, rewrite history or delete refs, or change a setting, a hook or an account is the owner's (specification 5 §11 point 6; A51 item (4)); any other entry may be approved by the decision agent, for the self-build only (A51; specification 5 §11 point 6). An entry never loosens the `git push` concern (specification 5 §11 point 5).
- Until a list exists at the base, both lists are empty and every shell call with a live tied lease is refused and, as a section 8 violation, ends the session (specification 5 §11 points 5 and 6) [src/aieos_bootstrap/claude_code_pretool_hook.py:74-82]. The reader accepted with TASK-076 reads both lists at the base from Git's object store, each in a fixed form narrower than YAML, voids a list with any entry outside the form, and gives the one list [src/aieos_bootstrap/claude_code_shell_allow.py:174-194, :219-259, :262-273, :276-312]; the PreToolUse program passes it for a Bash or PowerShell call on the judged path only, and the empty list for any other tool, a parse failure of the input, a reader failure or an answer of another shape [src/aieos_bootstrap/claude_code_pretool_hook.py:223-237, :327] (revision 9).
