## 2. The protocol's place

- Agents reach the core only through the protocol: "Chỉ AIEOS core ghi `.aieos/`; agent ghi qua protocol (MCP/CLI)" [AIEOS-concept.md:879]; the core writes through one writer [docs/specs/spec-02-aieos-file-format.md:45] (constitution INV-004). The server reaches the store and the event log only through the writer module's functions, never by opening their files itself (proposed), as specification 5 says of hooks [docs/specs/spec-05-adapter-contract.md:113].
- The MCP server is the core's interface, not an enforcement layer. A runtime reached only through MCP is at most tier T2, "Post-hoc + báo cáo có cấu trúc" [AIEOS-concept.md:651], as a target and unmeasured: a tier counts only when measured [docs/specs/spec-05-adapter-contract.md:31], and an unmeasured control is advisory (constitution OPS-003 [docs/pre-genesis/constitution.md:138]). An adapter declares its real enforcement level, not only that it "supports MCP" [AIEOS-concept.md:630]. What an agent does between calls is the adapter's (specification 5).

## 3. Transport, identity and the lease rule

- **Transport** (proposed): MCP over stdio, with JSON-RPC 2.0 messages; one server process per run of the runtime, started by the runtime inside a granted session.
- **Bootstrap limit** (proposed, stated as a limit): the bootstrap serves MCP in the Python 3 standard library only, with no MCP SDK (A9; constitution INV-002, INV-003). Whatever the protocol needs beyond that is out of the bootstrap.
- **Lifecycle outside the agent's calls:** the session's start, submission and end are made by the launcher, outside the runtime session they govern, never by the agent's tool calls [docs/specs/spec-05-adapter-contract.md:112]; no tool of this specification starts, submits, releases or ends a session.
- **Identity:** the server takes the session id, the project root and the base from the runtime's environment, where the launcher passes them [docs/specs/spec-05-adapter-contract.md:112]. Specification 5's text names only `AIEOS_BASE` [docs/specs/spec-05-adapter-contract.md:112]; the names `AIEOS_SESSION_ID` and `AIEOS_ROOT` come from accepted code (TASK-072), the PreToolUse program's [src/aieos_bootstrap/claude_code_pretool_hook.py:130-132] [src/aieos_bootstrap/claude_code_pretool_hook.py:9], and the server uses the same three. A call is tied to the session by that id and to the lease by the one lease the core's store holds for the session [docs/specs/spec-05-adapter-contract.md:113]. Whether a server started by the runtime inherits its environment is unmeasured, as it is for hooks [docs/specs/spec-05-adapter-contract.md:120].
- **The lease rule** (proposed, closed): every tool except `status` is refused unless the core's store holds a live lease for the session, a check of the store's lease, not of a token the agent carries, as for the read-set accumulation [docs/specs/spec-02-aieos-file-format.md:44]. No tool takes a fencing token. Each record a tool writes carries the fencing token of the lease the store holds for the session, taken by the core from the store, never from the agent, as specification 2 requires of every event that results from a lease holder's action [docs/specs/spec-02-aieos-file-format.md:133] [docs/specs/spec-01-state-and-event-model.md:49]. The commit's trailer and the launcher's submission carry the token as specification 5 says [docs/specs/spec-05-adapter-contract.md:24] [docs/specs/spec-01-state-and-event-model.md:113-114].
- **Weaker than fencing** (stated): any process holding the session's environment can call the writing tools while the lease is live; this check is weaker than the fencing of submissions [docs/specs/spec-01-state-and-event-model.md:114]. A lease that expires during the session makes every tool except `status` refuse with `lease_expired`; what a refusal records is section 8's.

## 4. The tools

Seven tools (proposed), "about eight" [AIEOS-concept.md:944], all used inside a granted session. They serve the steps of the session protocol that happen within it ("Boot … → Acknowledge (… mơ hồ → hỏi) → Work → Submit (diff + report) → Handoff" [AIEOS-concept.md:535]): Boot has `get_work_order`, Acknowledge has `acknowledge` and `ask`, Work has `query` for pull and no tool of its own, the report goes with `report`, Handoff has `handoff`, and `status` serves all; the submission itself is the launcher's. Errors are section 8's.

| Tool | Input | Output | Writes |
|---|---|---|---|
| `get_work_order` | — | the session's Work Order (section 5): Boot without chat history [AIEOS-concept.md:535]; the error `no_session` also when `AIEOS_BASE` is absent or not exactly 40 lowercase hexadecimal characters (revision 8) | nothing |
| `query` | `ref` | one item the Work Order holds, in full or by reference, as `{ref, hash, content}`; an item held by reference is answered from a second build of the same inputs with every budget unbudgeted and must carry the same hash (revision 8) ("Pull hơn push" [AIEOS-concept.md:515]), read only at the session's base, never from the working tree, as specification 5 reads the contract [docs/specs/spec-05-adapter-contract.md:113] (proposed); a ref the Work Order does not hold `out_of_scope`, and a ref whose full item cannot be produced `not_found`; `AIEOS_BASE` as for `get_work_order` (revision 8) | nothing; its reads are not in the observed read-set, which holds only what an adapter passes [docs/specs/spec-02-aieos-file-format.md:44] [docs/specs/spec-05-adapter-contract.md:71] (a stated gap, section 9) |
| `status` | — | `{task, lease}`, where `lease` is `live` with its expiry, `expired`, or `none` when the store holds no lease row for the session or the session has ended (a result, not the error `no_lease`); the error `no_session` when the environment holds no session id, no root, or no store at that root | nothing |
| `acknowledge` | `assumptions` (a list of strings) | the record ids | one `claim` record of the session per assumption [docs/specs/spec-02-aieos-file-format.md:146] [docs/specs/spec-02-aieos-file-format.md:149], carrying its `text` (section 11 point 5) (proposed); may be called more than once |
| `ask` | `question` (a string) | the record id | one `claim` record of the session carrying the question's `text` (proposed); how an answer reaches the agent is open (section 11) |
| `report` | `criteria` (a list of `{ac, text}`), `notes` | the record ids | the structured report (section 7): one `claim` record per criterion carrying its `text` and its AC id in `acs` (section 11 point 5), and one carrying `notes` as its `text` (proposed); may be called more than once |
| `handoff` | `done`, `not_done`, `assumptions`, `discoveries`, `risks`, `proposals` | the record ids | called once per session (a second call `invalid_input`), before the agent's run of the runtime ends, while the lease is live (proposed); one `claim` record of the session per item, at once, carrying its `text`, whose `refers_to` names the file `handoffs/<task id>-<session id>.md` and the item's list and place: for `discoveries` and `proposals` as specification 2 §5.2 says [docs/specs/spec-02-aieos-file-format.md:118], for the other four lists in the same form (proposed); the file itself is written later by the core (section 7) |

- Tool names, argument names, the JSON shapes and how many times each tool may be called are proposed; the handoff's six lists, its file name, and the claims of discoveries and proposals with their `refers_to` are specification 2's [docs/specs/spec-02-aieos-file-format.md:116-118].
- Assumptions given at `acknowledge`, before the work, and in the handoff, at its end, are both recorded, as two statements made at different times.
- Every claim record a tool writes has `subject` the task id, `source_class` `agent_declared`, `session` the session id, and `recorder` naming the MCP server and the session [docs/specs/spec-02-aieos-file-format.md:147-149] [docs/specs/spec-02-aieos-file-format.md:156] [docs/specs/spec-04-verification-and-evidence.md:62] (proposed).

## 5. The Work Order

- The Context Compiler turns project state and the task contract into the Work Order, "context tối thiểu đủ để làm task" [AIEOS-concept.md:510]. It is issued only after CONTINUE or CONTINUE_WITH [AIEOS-concept.md:506] [docs/specs/spec-03-resume-check-and-decision-engine.md:13]; CONTINUE_WITH compiles it again without changing the contract [docs/specs/spec-03-resume-check-and-decision-engine.md:148].
- **Form** (proposed): a JSON object returned by `get_work_order`, with `task`, `contract_version`, `contract_hash`, `base` (the session's `AIEOS_BASE`), `session_id`, `decision` (`CONTINUE` or `CONTINUE_WITH`, from the Resume Check record that made the grant [docs/specs/spec-03-resume-check-and-decision-engine.md:112-136]), `contract` (section 5's next point), `layers` (section 6) and `work_order_hash`, the SHA-256 of its canonical form without that field. The canonical form is a choice of this specification, not one of specification 2's hash rules [docs/specs/spec-02-aieos-file-format.md:22] (proposed): UTF-8, keys sorted, no insignificant whitespace.
- **The contract** (proposed): the field `contract` holds every key of the task contract as read at the base, specification 2's keys [docs/specs/spec-02-aieos-file-format.md:94-114], among them `objective`, `write_set`, `read_set`, `forbidden`, `capabilities`, `autonomy`, `verification_plan` and `exit_conditions`; so the Work Order carries the task's objective and the scope limits of the preventive layer [AIEOS-concept.md:554], beside the applicable constitution articles (section 6).
- **Compiled at the base** (proposed): the Work Order is compiled from the files at the session's base, the base branch's tip at the grant [docs/specs/spec-05-adapter-contract.md:112], and again at each call, with nothing cached, so `get_work_order` returns the same object only for as long as the task's last `task.approved` and last `decision.execution` stay the same; a new grant, or a later lease on another task in the same session, gives another object (revision 8). That base and the HEAD the Resume Check decided on can differ, a limit of the kind specification 5 states [docs/specs/spec-05-adapter-contract.md:121].
- **Where it is kept** (proposed): nowhere in revision 8. It is returned, not written as a file under `.aieos/` and not appended as an event. Given a Work Order, its hash can be checked from its own fields. Compiling it again needs its base, the Resume Check's record [docs/specs/spec-03-resume-check-and-decision-engine.md:112-136] and the session id the launcher made [docs/specs/spec-05-adapter-contract.md:112]; the base is kept nowhere but in the Work Order itself and the runtime's environment, so a later recompilation without it is not possible in revision 8. Keeping it or its hash anywhere would need a revision of specification 2 (its local store's tables [docs/specs/spec-02-aieos-file-format.md:44]) or of specifications 1 and 2 (an event); this is open (section 11).

## 6. The Context Compiler v1

- **Deterministic:** graph-based, no semantic search [AIEOS-concept.md:942]; "Chọn theo graph … không tìm kiếm mù" [AIEOS-concept.md:513].
- **Layers**, in the concept's order [AIEOS-concept.md:512]: (1) the constitution articles of specification 3's task-time set, which already includes the articles the contract lists [docs/specs/spec-03-resume-check-and-decision-engine.md:45] and carries out concept :393's rule [AIEOS-concept.md:393], taken from the Resume Check record's `constitution` key [docs/specs/spec-03-resume-check-and-decision-engine.md:129], not recomputed at the base (proposed); (2) the components whose `paths` meet the write-set or the declared read-set (specification 2's `components` [docs/specs/spec-02-aieos-file-format.md:83]) (proposed); (3) the specifications and acceptance criteria the contract traces to (`traces_to`, `acceptance_criteria` [docs/specs/spec-02-aieos-file-format.md:102] [docs/specs/spec-02-aieos-file-format.md:108]), with the ADRs that `traces_to` names; (4) the files at the base that match the write-set's patterns [docs/specs/spec-02-aieos-file-format.md:104] [docs/specs/spec-03-resume-check-and-decision-engine.md:56], a pattern matching no file giving none (proposed), and the files of specification 3's declared and derived read-sets [docs/specs/spec-03-resume-check-and-decision-engine.md:62-63], leaving out the observed source of its effective read-set [docs/specs/spec-03-resume-check-and-decision-engine.md:64]; (5) the task's last handoff [docs/specs/spec-02-aieos-file-format.md:116], where which one is "the last" is open, since the file names carry no order (section 11).
- **ADRs:** concept :100 has the Work Order carry the related ADRs [AIEOS-concept.md:100], but an ADR's front matter is only `id`, `version` and `title` [docs/specs/spec-02-aieos-file-format.md:80], and nothing links an ADR to a task. In v0.1 only ADRs that the contract's `traces_to` names are included (proposed); anything more is open (section 11).
- **The graph** (proposed): in v0.1 the traceability graph is the edges the files already declare: `traces_to`, the intent files' `components` and `interfaces`, and constitution `scope`; the code dependency graph is specification 3's derived read-set [docs/specs/spec-03-resume-check-and-decision-engine.md:63], which this specification uses and does not extend.
- **Items** (proposed): each item is `{ref, hash, content}`, or `{ref, hash}` when given as a reference.
- **The budget** (proposed, stated as a limit): a limit per layer in bytes, since the standard library has no tokenizer; over a limit, items of that layer are given as references, which the agent may pull with `query`; the order in which items are turned into references is open (section 11). Never a summary: a summary is a model call, and no core makes one (constitution INV-001 [docs/pre-genesis/constitution.md:28]); of the concept's "tóm tắt hoặc chuyển thành tham chiếu" [AIEOS-concept.md:514], only references are used.
- **The registry** [AIEOS-concept.md:516] (proposed): in v0.1 only the `interfaces` the intent files declare [docs/specs/spec-02-aieos-file-format.md:83].

## 7. The handoff and the structured report

- **The handoff** is specification 2 §5.2's [docs/specs/spec-02-aieos-file-format.md:116-118]: discoveries and proposals never become facts by being written [AIEOS-concept.md:537]. (proposed) The `handoff` tool records each item at once as one claim record of the session carrying its `text` (section 4); after the submission, or the session's end without one, the core writes `handoffs/<task id>-<session id>.md` from those records, in their order, with `commit` when the session submitted one. So the concept's order "Submit … → Handoff" [AIEOS-concept.md:535] and specification 2's `commit` [docs/specs/spec-02-aieos-file-format.md:118] both hold. With no `handoff` call, the core writes no handoff file (proposed); abnormal ends stay open as specification 5 leaves them [docs/specs/spec-05-adapter-contract.md:125]. How the file reaches Git (which tree, who commits it, how it stays out of the agent's commit) is open (section 11). Where the review queue of discoveries and proposals lives is open (section 11).
- **The report** (proposed): `{criteria: [{ac, text}], notes}`. Each criterion is recorded as one `claim` record of the session carrying its `text` and its AC id in `acs` as a list of one id, a use of `acs` that specification 2 now gives only to gate results [docs/specs/spec-02-aieos-file-format.md:152] and that the prerequisite revision widens (section 11 point 5); `notes` is one claim record with its `text` and no `acs`. A record whose recorder is the lease holder's session counts only as `agent_declared` [docs/specs/spec-04-verification-and-evidence.md:62], and nothing here raises it.

## 8. Errors

- (proposed) A closed vocabulary: `no_session`, `no_lease`, `lease_expired`, `not_found`, `out_of_scope`, `invalid_input`, `core_error`. The answer to an error is `{"error": <word>}`; for `core_error` of `get_work_order` and `query` it also carries `detail`, the list of the findings of the compilation: `{"error": "core_error", "detail": [...]}` (revision 8).
- (proposed) An error grants nothing and changes no task or lease state; a call the core cannot tie to a live lease is refused (section 3; `status` excepted). The refusals the other specifications record are still recorded as they say: a refused submission is an observation [docs/specs/spec-01-state-and-event-model.md:114] [docs/specs/spec-02-aieos-file-format.md:188], and a Resume Check that cannot read an input writes its record with `error` [docs/specs/spec-03-resume-check-and-decision-engine.md:86]; a refusal that one of this specification's own tools finds before its first append records nothing.
- (proposed) A lease that changes or expires between a tool's read of the lease and one of its appends is refused by the writer's fence, and the writer records that refusal as an observation, as a refused submission is recorded [docs/specs/spec-01-state-and-event-model.md:114]; the claims the same call appended before it stay, each a valid claim under the lease live at its append, and the tool answers the error (section 3).

## 9. Limits

- Unmeasured: nothing here has been measured; MCP alone is at most tier T2, as a target (section 2).
- The server cannot stop an agent from ignoring the Work Order or reading beyond it; reads stay declared or observed as specifications 3 and 5 say; the reads `query` serves are not in the observed read-set, which stays a lower bound [docs/specs/spec-02-aieos-file-format.md:185].
- The lease check is weaker than fencing (section 3); the standard-library limit (section 3) and the no-summary limit (section 6); the base at the grant against the Resume Check's HEAD (section 5).
- Overlapping write-sets never run in parallel in v0.1: one lease at a time [docs/specs/spec-03-resume-check-and-decision-engine.md:157].
